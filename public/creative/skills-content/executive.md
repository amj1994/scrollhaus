## What Executive is

Executive is a **polished, production-grade component system** expressed as implementation-agnostic design tokens. Its character is bright, friendly, and precise: off-white pages, crisp white controls and cards, deep slate actions, a playful but controlled accent palette, restrained shadows, and a modern system UI sans throughout. Components use 16px corners by default; only buttons, single-line inputs, alerts, and badges use 9999px pill corners. Checkboxes remain rounded-square at 6px. Spacious layouts and clear contrast make the interface feel approachable and product-focused.

### Signature traits — non-negotiable

These are what make a screen recognizably Executive. Hold every one of them, on every surface:

- **One 16px component radius with four pill families** (`radius.md`) — cards including carousel cards, dashboard widgets, table-card wrappers, modals, drawers, dropdown and popover panels, menu rows, tabs, groups, tooltips, textarea shells, and every free image/media corner use 16px. Top-attached product media keeps that radius on its outer top corners and uses square joined bottom corners with no divider. Only buttons, single-line inputs and selects, alerts, and badges resolve to the 9999px pill radius. Checkboxes retain a 6px rounded-square corner.
- **Functionally round controls** — toggle tracks, avatars, radios, range thumbs, status dots, and spinners stay fully round with `radius-full`.
- **Modern system UI typography** — headings, body, UI, and buttons share the system sans family. Headings use semibold 600 with gentle -0.01em tracking; body copy keeps a 16px floor with 1.6 leading; labels stay sentence case.
- **White sections with a fixed accent rhythm** — count the hero as section one. Sections one and two are square and white; section three is a centered pale accent surface with 24px corners. Repeat this two-white, one-accent rhythm down the page, cycling the four registered accent values `#E6DAFE` → `#FFF1BF` → `#C1EEEF` → `#FFE5F4`.
- **One bright page family** — the viewport, every navbar/top bar, every hero/page header, ordinary sections, and footer use solid white in a centered 1280px container. Colored sections are also capped at 1280px and centered, so their pale fill never becomes a full-width band.
- **Bright surfaces with quiet depth** — pricing and testimonial cards establish the universal shell: every card uses solid white, 16px corners, `spacing-6` (24px) content padding, and `elevation-1`. On white or neutral sections the outer edge is the same 1px `default-subtle` gray hairline as section dividers; on any colored or dark section the white card has no visible outer border (`1px transparent` preserves its geometry). Internal dividers stay `default-subtle` in both contexts. Composite and edge-to-edge media cards apply the same 24px inset to each content cell or body region without adding a second outer frame. Buttons use the exact solid `brand` fill with no outer elevation and no inset shadows or highlights; their lower tonal edge is a maximum of 1px. Inputs stay flat with clear borders and focus rings.

## How to use this skill

1. **Load the foundation first.** For any UI work, read `colors.md`, `typography.md`, `spacing.md`, `radius.md`, `shadows.md`, `motion.md`, and `responsive.md` before anything else — every component depends on them.
2. **Add a module per element on the page.** A modal form with inputs and buttons means `modal.md` + `input-field.md` + `buttons.md`. Don't write implementation until the relevant specs are loaded.
3. **Cross-reference.** Components inherit from each other — a search bar satisfies the search section in `input-field.md`; a table footer pulls in `pagination.md`.
4. **Trust these files over memory or external docs.** When this skill and any external or vendor documentation disagree, this skill wins.

## Operating rules

- **No em-dash / en-dash in UI copy.** Never use `—` or `–` in any string the user reads (headings, body, labels, buttons, microcopy); rewrite with a comma, period, colon, or parentheses. Hyphens only inside compound words. See `typography.md`.
- **Outline and solid buttons are the same height.** A button's height is identical whether it is **solid or outline** — the border sits _inside_ the box (`box-sizing: border-box`) and **never adds height**, so the two variants align pixel-for-pixel in a row. See `buttons.md`.
- **Button labels never hide on small screens.** A labeled button keeps its visible text at **every** breakpoint — never collapse "New run" into a bare `+` icon on mobile. When a row runs out of space, adapt the layout instead: wrap, stack, go full-width, or drop/relocate a whole lower-priority control into an overflow menu. Only controls _designed_ icon-only at all sizes (bell, hamburger, close ✕, theme toggle — always with an accessible name) are exempt. Hiding a label with `display: none` inside a breakpoint is prohibited. See `buttons.md`.
- **A designated two-button row is one non-wrapping unit.** When exactly two related landing-page actions are presented as a paired row, they remain beside each other on one line at every viewport, keep the same context tier and height, retain both visible labels, and use one consistent gap. On the narrowest screens, shorten the labels first; if more room is still required, reduce only the pair's inline padding while preserving the documented height, type, icon, and touch target. Never let one button wrap below the other or allow either label to break onto two lines. See `buttons.md` and `responsive.md`.
- **Use the two-tier button hierarchy by context.** Landing-page content uses **Base: 42px high with 24px inline padding**. Application and dashboard actions, navbar and footer actions, and microcomponents use **Small: 36px high with 18px inline padding**; Small icon-only controls are 36 × 36px. The legacy Large alias resolves to Base. Labels use the system sans at semibold 600, 14px, sentence case, and every button uses the 9999px `radius-full` pill corner.
- **Tokens are the vocabulary, and they are implementation-agnostic.** Use semantic tokens such as `neutral-primary-soft`, `heading`, `spacing-4`, `radius-xl`, and `elevation-1` without renaming them.
- **Hold the signature radius.** The normal component scale resolves to 16px. Cards including carousel cards, application/dashboard widgets, table-card wrappers, overlays, menus, tabs, groups, tooltips, and textarea shells use that 16px corner. Only buttons, single-line fields and selects, alerts, and badges use `radius-full` at 9999px. Checkboxes use a 6px rounded-square corner. Ordinary white sections, heroes, and footer bands use `radius-none` (0px); the scheduled centered colored sections use exactly 24px corners.
- **Bright, quietly elevated panels; subtle borders on controls.** Every card uses solid white, an explicit 16px radius, `spacing-6` (24px) content padding, and `elevation-1`, regardless of viewport or card variant. On white and neutral sections it uses a 1px `default-subtle` hairline matching section dividers; on colored and dark sections that outer hairline becomes transparent so the white card has no visible outline. Pricing columns and testimonial cards use this exact conditional edge rule. Composite and edge-to-edge media cards move the same 24px inset to their content cells or body region so the outer frame is not padded twice. Controls use a 1px `default` edge; focus switches to `brand` with a soft `brand-medium` ring. Internal seams always use `default-subtle`.
- **Every component border is exactly 1px maximum.** Outer edges, control outlines, table/card borders, dividers, joined-control seams, active-tab indicators, accent edges, and decorative component keylines all use a single 1px hairline; no visible component border may be 2px or thicker. Accessible focus rings remain separate `box-shadow`/outline indicators and do not increase the physical border width.
- **Bright page; deep slate is the brand color.** Every navbar/top bar, hero/page header, ordinary section, and footer uses `#FFFFFF`. Every third eligible content section follows the contained accent cycle `#E6DAFE`, `#FFF1BF`, `#C1EEEF`, `#FFE5F4`. `brand` (`#2B2D42`) leads controls and compact highlights, while `fg-brand` carries readable links. Brand actions stay inside the slate brand family; never substitute the standalone teal or a status hue.
- **The footer is one flat surface.** All footer bands share the bright neutral page surface and use only subtle 1px internal dividers; do not add gradients or a second footer tint.
- **Equal vertical breathing room between sections.** Every section carries the **same spacing above and below it** — the top padding/margin of a section equals its bottom padding/margin, and the gap between any two adjacent sections is symmetric. And the **spacing between any two adjacent sections is identical the whole way down the page**: one uniform vertical rhythm from the first section to the last — a section never introduces a custom, larger, or smaller gap than its neighbours. No section gets more air on one side than the other; rhythm comes from this consistent, balanced spacing, never from uneven gaps. See `spacing.md`.
- **Section vertical padding is 96px, top and bottom.** Every content section uses equal `spacing-24` (96px) padding on large screens and equal `spacing-12` (48px) padding below 768px. This symmetric value stays consistent from the first section to the last.
- **Footer spacing is balanced.** Use 96px top and bottom on large screens and 48px top and bottom below 768px, unless a final legal row owns the bottom inset; in that case subtract that inset from the outer footer so the visible spacing remains balanced.
- **If the footer's last band already carries its own bottom padding, the footer container drops its bottom padding entirely (never double it).** When the final row of the footer — the bottom bar / copyright band, or whatever sits last — already has its **own `padding-bottom`** (e.g. a bottom bar with `padding-block`), the **outer footer container must set its own `padding-bottom` to `0`** so the two don't stack into an oversized gap. Only **one** element owns the footer's bottom spacing: either the container pads the bottom **or** the last band does — never both. So a bottom bar with, say, `spacing-8` of block padding means the container's bottom padding is `0` (the top padding still follows the 96/112px rule above). If the last band has **no** bottom padding of its own, then the container supplies the light bottom padding from the rule above. Audit the real rendered footer: if you see a large empty band below the last row of content, it is almost always this doubled padding — zero one of the two.
- **Foundation values are law.** Never invent a color, size, radius, or shadow that contradicts the foundation files — if no token fits, the foundation file is where a new one gets added.
- **Closed intent families apply only to alerts and badges.** Every alert and badge uses the darker foreground and tonal edge from its own intent for its root and every descendant: brand/info uses `fg-brand-strong`, success uses `fg-success-strong`, danger uses `fg-danger-strong`, and warning uses `fg-warning`. A default alert is a compact, content-height row with `spacing-3` block padding, `spacing-4` inline padding, and its leading icon, message block, and visible 20 × 20px dismiss control vertically centered on one axis; never force the dismiss control to the standard 36px button box or give the alert a fixed/minimum height. Do not propagate the intent-family rule to cards, panels, mockup screens, navigation, pagination, tabs, segmented controls, or buttons. Cards always remain white with normal `heading` and `body` content; primary and status actions use white labels on their solid intent surface.
- **Every interactive element earns its states.** Hover, focus, and disabled are defined in each module; the brand focus ring is never removed without an accessible equivalent.
- **Button hierarchy is visible and consistent.** Primary and status buttons keep white text over the exact solid `brand` fill at rest and fade a solid `brand-light` overlay over that continuously painted face. Secondary uses `brand-softer` with `fg-brand-strong` text and moves to `brand-soft`; outline uses a white face with `fg-brand-strong` text and moves to `brand-softer`. Ghost and link actions remain transparent. Every variant keeps a maximum 1px token-derived edge, no outer or inset shadow, and no native tap flash.
- **White-surface CTAs use only Primary Brand or Secondary.** On a white page surface or inside a white card, the single leading CTA uses Primary Brand and supporting CTAs use Secondary. Outline, Ghost, and Link are reserved for explicit component demonstrations and specialized utility contexts, not ordinary white-surface page/card actions. Every ecommerce product-card purchase or add-to-cart action is Primary Brand on its white card.
- **White cards are neutral control boundaries.** Buttons, inputs, selects, textareas, and other controls inside a white card always use their canonical Executive background, border, foreground, hover, active, and focus tokens, even when the card sits inside a lavender, warm-yellow, cyan, pink, or dark section. Only controls placed directly on the colored section surface receive that section's tonal treatment. In a tonal commerce/product section, the toolbar and pagination may use the parent accent family because they sit directly on the section, while controls inside each white product card remain canonical. Content actions retain Base geometry while navbar, ecommerce toolbar, pagination, and footer actions retain Small geometry. Standalone tabs remain a separate microcomponent; ordinary fused button groups and segmented controls keep their documented neutral treatment.
- **Semantic HTML, always.** Proper `h1`→`h6` order, `<button>` for actions, `<a>` for navigation, real labels on form controls, and ARIA where a module calls for it.
- **No vendor leakage.** Describe and implement through tokens; never paste vendor-specific implementation strings from external docs into the work.
- **Form controls share one shell.** Text-like controls (`input-field`, `select`, `textarea`, …) inherit the field shell in `input-field.md` unless a module explicitly overrides it.
- **Themed form controls.** Checkboxes, radios, and toggles always render in **this theme's own style** — the theme `brand` fill when checked / selected / on, plus the theme's surface, border, radius, and focus-ring tokens — never the native/unstyled browser control and never another theme's colors. **Reset the native input** (the platform appearance reset) and draw the control yourself — a native `accent-color` tint alone is **not** enough, it still renders the OS control: build the box / track, the checked `brand` fill, the check / dot / thumb mark, and the focus ring from this theme's tokens. See `checkbox.md`, `radio.md`, `toggle.md`.
- **Radio inputs are always true circles.** Every radio control uses `radius-full` / 50% on an equal-width-and-height box in every state. Checkbox boxes remain 16 × 16px with the explicit 6px exception.
- **Coherent outline icons.** Use one product-supplied outline icon set throughout, sized and colored with tokens; avoid emoji, mixed icon styles, or one-off drawings.
- **Production charts use the dedicated five-color series palette.** Bind dashboard data to a real charting component and assign visible series in the fixed `chart-1` → `chart-2` → `chart-3` → `chart-4` → `chart-5` order. Keep these tokens exclusive to charts, preserve the mapping in legends and tooltips, and never substitute brand, section, or status colors for categorical series. Do not use static images or placeholder bars.
- **In-palette imagery — no stock photos, no bare-icon placeholders.** Product shots, category media, carousel slides, and every other content image render as **placeholder artwork drawn entirely from the theme's own tokens** — a soft light gradient field with a fine low-opacity texture and a polished composed vector scene, never a repeated generic icon. **Images and illustrations never carry an outer border** on either the artwork or its media wrapper; surface contrast, spacing, and clipping define the boundary. Internal SVG strokes may describe objects within the artwork, but they never frame the illustration itself. Every content image, artwork surface, preview, and media frame uses an **explicit 16px corner radius** and clips overflow to that shape. Top-attached product media is the joined-edge exception: it keeps 16px on its two outer top corners, uses `radius-none` on both bottom corners, and has no bottom border or divider before the card body. The artwork **fills its media frame edge to edge** (cover/slice cropping, centered); **never render media as a lone small icon centered on a gray tile**, and **never hotlink or bundle external photographs** (no stock-photo URLs, no third-party image hosts). When a brief explicitly makes a commerce/product section tonal, its product artwork derives every fill, frame, texture mark, and caption bar from lighter and darker shades of that section's parent accent; do not introduce a brand, status, or chart-series hue into the artwork. The only verbatim external assets are **user-supplied brand files** (e.g. partner logos), served exactly as provided. Decorative section illustrations are likewise in-palette vectors or supplied assets. Functionally circular avatar images remain the documented round-control exception.
- **Spacing comes from the fundamentals.** Take every margin, padding, and gap from the scale in `spacing.md` (never ad-hoc px). Always give **headings and paragraphs room above and below**, and **pad both sides of any border, separator, or divider** so content never crowds a rule. See `spacing.md` and `typography.md`.
- **Every navbar is solid white.** Marketing, storefront, application/dashboard, and component-library navigation bars always use the opaque white surface token at every breakpoint and in every sticky state. Do not tint, color, darken, gradient, pattern, or make a navbar translucent. Use deep charcoal links and one subtle hairline when separation is needed. Keep actions consistent with the standard buttons.
- **Marketing navbar CTA hierarchy.** The marketing navbar's “Get started” action uses the documented **Secondary** button treatment (`brand-softer` face, `fg-brand-strong` label, 1px `brand-soft` edge), at the Small 36px navbar size. Reserve the solid Primary Base-size treatment for the hero's leading CTA.
- **Hero buttons use the standard hierarchy.** A primary hero action uses the exact solid `brand` face with white text; a supporting hero action uses the documented secondary or outline treatment. Hero, pricing, CTA, footer, application, ecommerce, and component-library actions share the same variant states, no outer or inset shadow, and the 9999px pill corner. See `buttons.md`.
- **Navbar & footer links are text links, not buttons.** A link in the navbar or footer has **no padding and no background/fill hover** — it is **not** a ghost button. On hover it only **lightens its text color** (a subtle lighter/dimmer text tone) because it is a link, not a button. Reserve padded, background-hover treatments for real buttons and sidebar nav items. Adjacent nav links sit **24px** apart.
- **Section width: max 1280px, centered.** Every section, navbar, and footer aligns to one centered 1280px content container. White sections always keep exactly 48px of left and right inner padding at every viewport; never remove this inset on wide screens or change it at intermediate breakpoints. Colored section surfaces stop at 1280px and use 24px corners. Marketing, storefront, and component-library pages draw one continuous 1px `default-subtle` rail on each side of the 1280px page shell, running without breaks from navbar through footer; individual section containers do not restart these borders. Every section also draws a full-viewport 1px top border and 1px bottom border in that exact same `default-subtle` color, including sections whose colored surface stops at 1280px. Dashboards are the exception to the page-side rails and use only their documented application-shell and functional component borders.
- **Executive content surface — 1280px centered content (marketing / storefront only).** Sections, hero, and footer use white around a centered 1280px content container with a fixed 48px left and right content inset at every viewport. After two white sections, the next section receives the scheduled pale accent across that 1280px surface only.
- **Section header → content gap: 48px on large screens.** The **section heading block** — the section heading, plus any lead paragraph and/or buttons that belong with it — is separated from the **rest of the section's content** by a **48px**. Keep the heading, its paragraph, and its CTA buttons together as one intro block (their own internal gaps follow `typography.md` / `spacing.md`), then leave **48px** below that whole block before the body content begins. **Below the `sm` breakpoint (768px) this header → content gap steps down to 32px** — the one responsive step, applied equally on every section.
- **Section header max-width: 768px.** A section header — made up of any combination of an eyebrow, a heading, a supporting paragraph, and/or buttons (whichever the section uses) — is capped at **768px** wide (centered for centered headers, left-aligned within that measure otherwise) so the heading and lead wrap to a comfortable line length instead of stretching the full section width.
- **No decorative dashes or numbering in copy.** Never trail a word or label with a dangling dash flourish (e.g. `platform —`), and never number eyebrows, section labels, steps, or list items with zero-padded or hashed sequences (`01`, `02`, `#1`, `#2`). Eyebrows and headings are plain words: no dash "lines", no decorative counters.
- **No accidental duplicate borders inside components.** Where stacked cards, rows, widgets, or list items share an edge, only one child draws that internal border. Section boundaries are the explicit exception: every section intentionally owns both a top and bottom 1px `default-subtle` hairline.
- **Full-width section boundaries are mandatory and never doubled.** Every content section, including the hero, is visually bounded above and below by a 1px `default-subtle` rule across the full viewport width, using the exact same color as the 1280px container rails. Adjacent regions share one rule: the first unpreceded surface owns the top rule, and every section owns its bottom rule, which also serves as the next section's top rule. If a navbar or category nav already paints the preceding bottom edge, the following hero or section must not paint another top edge. Never render both sides of one seam, stack two 1px rules, or allow a 2px boundary. Rules stay full-width when a colored surface is capped at 1280px.
- **Input focus = a deeper shade of its own fill.** On focus, an input's border and ring are the **same colour as the input's own background, darkened** (a deeper tint of the field fill) — a soft glow that reads as active without introducing a foreign colour.
- **Chart tooltips are 16px data cards.** A chart tooltip is a multi-row data surface, not a pill label: its white shell uses an explicit 16px radius and `elevation-2`. Its outer edge follows the card rule, 1px `default-subtle` on white/neutral surfaces and 1px transparent on colored/dark surfaces; internal row separators remain `default-subtle`. Each row uses the exact series color on its swatch while its label and value use readable `heading` text, preserving a 1:1 mapping without using pale chart colors as small text.
- **Button groups use one gray state surface and own each edge once.** A fused button or segmented-control group uses one white `neutral-primary-soft` shell with one 1px `default` perimeter edge. Segments have no individual perimeter borders and stay white at rest; only each segment after the first draws one 1px `default` start-edge divider. Hover, press, and selected states use only `neutral-secondary-soft` with `fg-brand-strong` text/icons. The perimeter and dividers never recolor, and no underline, bottom rule, inset line, shadow, gradient, or additional border may indicate state. Focus adds only the standard focus ring. Never overlap bordered segments or allow adjacent cells to produce a doubled seam.
- **Button type & icon sizes.** Every button label is **14px** and every shaped-control icon is **16px**. Base and Small differ only in box height and inline padding; family, label size, weight, icon size, radius, and states stay identical. The **gap between a button's icon and its label is 6px**.
- **One font and one weight on EVERY button-shaped control — button groups and segmented controls included.** Every button and every button-shaped control renders in the **exact same font family (the UI sans) and the same weight (`font-weight-semibold`, 600)**, at the one **14px** label size, sentence case, normal tracking. Button groups, segmented controls, dropdown triggers, pagination, pills, and tabs are microcomponents and therefore use Small geometry. See `buttons.md`.
- **Button tier placement is binding.** Landing-page hero, section, card CTA, and content actions use Base. Application/dashboard actions, navbar and footer actions, dialogs, drawers, dropdown actions, and every microcomponent use Small. Large is a compatibility alias for Base; no third size is introduced.
- **Button variants are identical inside every white card.** Primary uses the solid `brand` treatment, Secondary uses the pale `brand-softer` treatment, Outline uses the white face with a `brand` edge, and Ghost or Link stays transparent. A button placed directly on a colored section may use that section's tonal family, but the treatment stops at the boundary of every white card. Every variant keeps the same 9999px pill radius, semibold label, maximum 1px edge, no outer or inset shadows, and documented hover and focus behavior.
- **Adjacent controls share the tier required by their context.** A landing-page content row uses Base throughout. A dashboard, navbar, footer, dialog, drawer, or microcomponent row uses Small throughout. Never mix 42px Base and 36px Small controls in one row; dropdown/select triggers and paired fields match the surrounding button tier. See `buttons.md` and `dropdowns.md`.
- **Landing-page check lists.** A list whose items lead with a **check icon** (feature ticks, plan inclusions, CTA reassurances) always renders the icon at **16px**, with a **16px gap** between the icon and the text, and the item text at **font-weight-medium (500)**. A bare check uses `heading`; a check inside a pale colored shape uses the darker foreground derived from that shape's own hue.
- **No decorative index numbers on landing pages.** It is **strictly forbidden** to prefix feature cards, steps, benefits, or any list item with a zero-padded ordinal (`01`, `02`, `03`) or any decorative counter on marketing / landing surfaces. Let the heading and copy carry the order and hierarchy — never a numbered badge, eyebrow, or "step 01" label. (Genuine data — a real count, a price, a stat value — is not a decorative index and is fine.)
- **Icon sizing and landing-page color.** An **18px icon is reserved for extra-large** contexts only; default UI icons stay smaller (≈14–16px). **Breadcrumb icons are ≤ 14px.** Always use the outline style (see the icon-library rule). Only standalone decorative, feature, checklist, contact, and store pictogram icons on a landing page use `heading`, never `brand` or `fg-brand`. An icon inside a button, link, alert, badge, tab, field, menu item, or any other labeled component inherits that component's exact text color in every state. The one size exception is the bare marketing pictogram: on landing-page feature and stat blocks, an icon that sits directly on the surface with no shape behind it renders at 36px in `heading`, with a fixed 16px gap between the icon and the text beneath it.
- **Shaped icons use the darker shade of their own shape.** On landing pages, an icon inside a pale brand or accent tile uses the corresponding darker foreground from that exact hue family; a white or neutral shape uses `heading`. The shape may keep its tinted surface and tonal edge, but the icon never switches to an unrelated brand or neutral color. Keep icon tiles at the universal 16px component radius and low contrast.
- **Table icons are 16px, never larger.** Any icon placed **inside a table** — a data table or a pricing / comparison table — is capped at **16px** (a `check` / `minus` / `x` cell mark, a sort caret, a row-action glyph, an inline status icon, etc.). Never let a table icon grow past 16px; if it sits in a tinted "chip" (e.g. a success circle behind a check), it may go **smaller** (~14px) so the icon reads comfortably inside its container, but 16px is the hard ceiling.
- **Dropdown panel border & shadow.** Every dropdown / menu panel carries a **border in its own background colour, darkened just enough to be visible** — a subtle darker edge of the panel's own fill, never a harsh contrasting line — plus a **medium drop shadow** so the menu lifts cleanly off the page.
- **Dropdowns and popovers use exactly 16px corners throughout.** The floating panel, menu items, and option rows use the 16px component radius on desktop and mobile. A trigger keeps a pill only when it is an actual button or single-line input/select.
- **Dropdown menus never scroll by default.** A dropdown / menu panel shows **all of its content at once** — no internal scrollbar, no capped `max-height`, no `overflow: auto/scroll`. Every item is visible and the panel grows to fit its items. Add a scroll area **only when the prompt explicitly asks for it** (e.g. a long searchable list); absent that instruction, never clip or scroll the menu. The panel always carries the **medium shadow** (see the dropdown panel rule above).
- **One hover background for every link surface.** Wherever a link or menu item shows a **background on hover** — top-nav links, sidebar links, dropdown / menu items, command-palette rows, tab-style links — it uses the **same single hover-background tint** (one subtle neutral fill), so the hover feedback is identical across navbars, sidebars, and dropdowns. Choose one value for this and reuse it everywhere — never give the sidebar one hover colour and the dropdown another. The **active / selected** state is a separate, stronger background (a brand tint), likewise reused consistently across all of these surfaces.
- **Selected table rows use the neutral hover background, not a brand tint.** A selected row takes the **same subtle neutral background a row shows on hover**, never a violet brand-tinted fill. A row that is both **selected and hovered stays that exact same colour** (no deepening, no shift). Selection is signalled by the row's checkbox / control state, not by recolouring the row.
- **Textarea corners stay 16px.** A textarea and its composite wrapper use the universal component corner, while single-line fields remain 9999px pills.
- **Application widget grid gap is 16px.** On application / dashboard pages, the gap between widgets in the layout grid — both the row and column gutters between cards/widgets — is **16px**.
- **Widgets in the same grid row share the tallest widget's height — set a floor, never a fixed height.** A widget that needs a canvas (a chart, a gauge, a map) declares **`min-height`**, never `height`. A fixed height *locks* the widget, so when a taller sibling sits beside it in the same row the short one refuses to stretch and leaves a dead gap under its content, while the row's own height is set by the tall one anyway. With `min-height` the widget keeps a readable floor and still stretches to the row, and its chart area (the `flex: 1` fill) grows into the extra space. Widgets in a row are always flush top **and** bottom.
- **Widgets never carry their own outer margin — the container's `gap` owns the vertical rhythm.** The dashboard's widget column is a single flex/grid container with **one** `gap: 16px`; every widget and widget-row is a child of it. A widget must not add `margin-bottom` "to space itself", because the moment one widget does and its neighbour doesn't, the rhythm silently breaks (a standalone widget lands flush against the next with a 0px gap while gridded rows keep theirs). **One spacing source, no exceptions.**
- **A height-constrained scroll column must not squash its children.** When the dashboard's main column is a flex column with a constrained height and `overflow-y: auto`, its children inherit `flex-shrink: 1` — so the browser will **shrink every widget to fit the box instead of letting them overflow and scroll**. Tall widgets collapse (a data table crushes to a strip and, if it clips its own overflow, vanishes entirely). Pin the children: **`> * { flex-shrink: 0 }`**, so the column scrolls instead of crushing its content.
- **A scroll container must be a containing block.** Any element with `overflow: auto/scroll` also needs **`position: relative`**. Otherwise an absolutely-positioned descendant with no positioned ancestor (a visually-hidden input, an sr-only label, a decorative layer) anchors to the *initial containing block*, **escapes the scroll container entirely**, and stretches the document — producing a phantom second scrollbar and a long run of dead space below the page. The shell fits the viewport, yet `<html>` scrolls: that is always this bug.
- **Hero H1: up to 64px, 1024px max-width.** The hero's `h1` is the largest type on the page — **64px** on large screens (it may scale down only on narrow mobile viewports for fit). **The one exception is the storefront search hero** (display title + joined search group + deal carousel sharing the brand band): its title runs a fluid **36px → 60px** so the search group and carousel fit the band comfortably — it stays the largest type on the storefront page. Its text wraps within a **1024px** max-width so a long headline breaks onto a tight, readable column instead of running full-width. The **H1 carries a 24px `margin-bottom`**, which sets the gap down to the supporting paragraph. The supporting paragraph (hero lead) that follows the H1 is **20px** on large screens and scales **smaller on mobile** (≈16–18px), and it **also carries a 24px `margin-bottom`** — separating it from the CTAs / content below. The 24px on the H1 already provides the gap above the paragraph, so the paragraph takes **no separate top margin** (never stack a second gap on top of the H1's 44px).
- **Every non-hero page and section heading matches “Why us?”.** Use the same fluid **24px → 36px** size and **semibold 600** weight for marketing/storefront section headings, application page titles, and component-library category headings. The hero H1 is the only page-heading exception. Do not promote card, widget, modal, alert, or footer titles to this role; they keep their smaller component typography.
- **One element owns the vertical padding — never two nested.** When a band, card, or CTA sits inside a section, **only one of them adds vertical padding**. A section and an inner band must not both pad top/bottom, or the block bloats and reads off-center. Decide which container owns the vertical rhythm and zero the padding on the other.
- **Newsletter / signup bands get a dedicated layout — not the button-actions slot.** A CTA that holds an **email field + submit button** is a signup row, not a button group: never drop it into a `cta-card__actions` (or any container built for side-by-side buttons). Build a dedicated band — a **two-column grid on desktop** (copy left, form right) with a **hero-style signup row**: a **full-width field shell + Base button, inline from ~640px up and stacked below that**. Give it a responsive title, a `font-size-lg` description, and a small helper line (e.g. "No spam. Unsubscribe anytime.") under the form. **Never a fixed narrow field width** (e.g. 18rem) beside the Base button — the field flexes to fill the row.
- **Reset native element margins inside cards.** Elements the browser margins by default — `<blockquote>`, `<figure>`, `<p>`, `<ul>` / `<ol>` — are set to **`margin: 0`** whenever they are, or sit inside, a card. Otherwise the user-agent's default margin leaks **outside** the card border and reads as phantom padding around the box (a `<blockquote>` testimonial card is the classic trap). All spacing comes from the card's own padding. Also delete dead modifier classes that style nothing (e.g. unused `--1` / `--2` / `--3` variants).
- **Never delete a style rule without proving nothing uses it.** Before removing or "deduplicating" any style, **search the whole codebase for every class / selector it targets** (markup, components, templates, JS) and confirm **zero** references remain. A selector that appears only once in the stylesheet is **not** dead if any element still carries that class — deleting it drops that section to **unstyled HTML**. Deduplicate by **consolidating** repeated declarations into one rule, never by blindly deleting; when in doubt, keep it. After any CSS cleanup, **load the page and confirm every section still renders styled** — then hard-refresh (the dev server may still serve the old CSS bundle).
- **Zero a list's default left padding, not just its margin.** A `<ul>` / `<ol>` used as a layout row, nav, or menu carries the browser's default **~40px left padding** (`padding-inline-start`, reserved for bullets) — `margin: 0` and `list-style: none` do **not** remove it. Explicitly set **`padding: 0`** (or `padding-inline: 0`); if you only set `padding-block`, that left inset stays and the whole row is pushed ~40px inward, misaligning it with the logo / page container. Let the page container own horizontal alignment — the list contributes no indent of its own.
- **Sidebar links: the same contrasting background on hover and active.** Every nav link in a sidebar shows a **background fill on both hover and its active / current state, and it is the same fill** — a shade **darker than the sidebar's own background** so it reads clearly against it. The fill has **16px (`radius-md`) corners matching this theme**, never a foreign radius. Hover and active look identical in shape and colour; the active item may add a text / icon emphasis (weight or a brand tint) but the background stays that one shared lighter fill.
- **Navbar buttons use Small and one weight; no underlines on nav / sidebar links.** Every navbar button uses the 36px Small box, 18px inline padding, and semibold 14px label. **Underlined text is never allowed, in any state** (default, hover, focus, active), for **navbar links, navbar buttons, or sidebar links / buttons** — these navigation targets signal interactivity through colour and background, never an underline.
- **Translucent backgrounds must blur what's behind them, but cards and navbars are never translucent.** Any allowed overlay or glass panel with a **semi-transparent / translucent fill** must pair that translucency with a backdrop blur and an opaque fallback. Cards, navbar/top-bar, and hero/page-header surfaces are excluded because their required background is always solid white.
- **Badges are always width auto — never full-width.** A badge / tag / chip / status pill sizes to **its own content** (`width: auto`, an `inline-flex` / `inline-block` box that hugs its label + optional icon). It **never stretches to fill its container** — no `width: 100%`, no block/flex that spans the row, no `flex: 1`, no `align-items: stretch` pulling it edge-to-edge. Several badges in a row sit side by side (and wrap) at their natural widths, each only as wide as its text.
- **Pricing card: 24px between the price and the CTA button.** In a pricing card, leave **24px** between the **price line** (e.g. `$249/month`) and the Base CTA button tied to it. Apply it consistently across every card so prices and buttons line up row-to-row.
- **Avatar-only triggers carry no chevron.** In a navbar / top bar, an **avatar shown on its own** (just the photo / initials circle) is itself the trigger — do **not** put a chevron caret beside a bare avatar. A chevron is added **only when the avatar is paired with a visible label** (the person's name / role): `avatar + name → chevron` is fine, `avatar alone → no chevron`. A lone avatar plus a chevron reads as clutter; the avatar is already the affordance.
- **Joined input + button groups square the shared edges.** When an input is **attached to buttons (or addons) on its left and/or right** — a search-with-button, a stepper, a prefix/suffix group, any segmented control where an input touches a button — the **touching edges are squared to `0` radius** so the pieces read as one seamless control. An input with a button on **both sides** has **no border radius at all**; with a button on one side it keeps the theme's radius on the free side and `0` on the joined side. Only the **outer corners of the whole group** carry the theme's normal radius. Critically, the input's **focus border / ring must follow that squared corner too** — never let a rounded corner (or a rounded focus outline) peek out at the seam when the input is focused; the focus state matches the 0-radius joined edge exactly.
- **Card headings are 20px.** A card's heading / title — ecommerce & product cards, feature cards, pricing cards, testimonial and content cards, and cards in general — is **20px**. The **one exception is dashboard / application widgets**: a widget's heading follows the smaller, dense widget-title scale, not this 20px card-title size.
- **Ecommerce navbar collapses to one row on mobile.** On narrow viewports (**< 768px**) the ecommerce header is a **single bar** — logo at the inline start, a **hamburger menu button** at the inline end. The desktop secondary content **collapses off the bar**: the search field, cart / account actions, and the whole category row are **hidden** and move into a **menu panel that opens below the bar** (search + category links + a **"View all categories"** entry). On desktop the full **two-level layout** returns — search + logo + cart / account on the top row, categories on a row beneath. Use the **same hamburger + collapsible-panel pattern as the marketing navbar** so both headers behave consistently.
- **Modals use quiet depth.** A modal uses white, `radius-xl` (16px), a subtle hairline, `elevation-4`, and a dimming scrim. Internal header and footer rules use `default-subtle`.
- **Heading line-height follows scale.** Display headings use 1.05 leading; standard headings use 1.1; body copy uses 1.6. Keep headings semibold and system-sans.
- **Card treatments live in `cards.md`.** Every card uses a solid white surface, 16px corners, `spacing-6` (24px) content padding, and `elevation-1`. Its outer edge is 1px `default-subtle` on white or neutral sections and 1px transparent on colored or dark sections; internal seams remain `default-subtle`. Neither surface, geometry, inset, nor elevation changes with viewport, intent, variant, or hover state. Composite and edge-to-edge media cards put the same inset on their cells or content body.
- **No hover glow anywhere.** Cards and tables never glow, change elevation, or track the cursor; table rows use only the documented neutral hover tint.
- **16px floor for body & reading text.** No **body / paragraph / content text** on a page renders **below 16px** — hero leads, section descriptions, card body copy, list-item prose, and any running text sit at **≥ 16px**. The **only** exceptions are genuine **micro-elements** — badges, chips, tags, table meta / captions, helper & hint microcopy, eyebrows, and similar tiny labels — which may drop below 16px per their component specs. **Never shrink page body copy below 16px to make it fit** — if space is tight, cut words, not the size. This raises the reading-text floor above the 14px control baseline: interactive control labels and the micro-elements above may still use the compact scale, but the text a visitor actually reads does not.
- **Inline input + button pairs are width-bounded.** Wherever an input sits next to a button in one row — a newsletter signup, sign-in, search, or promo field, in **any section, on a landing page, a dashboard, or inside a card** — the **input is never wider than 400px**, and the **whole group (input + button together) is never narrower than 440px nor wider than 600px**. In practice: clamp the group to a **440–600px** band and cap the input at **≤ 400px** inside it (the button takes the remainder). This keeps the field comfortably sized and the pairing balanced — never a stretched full-width input, never a cramped one. Below the group's min width (narrow mobile), stack the button under the input rather than shrinking either past these bounds.
- **Every input shows a brand border on focus — no exceptions.** Any focusable field — a text/email/password input, textarea, select, a search bar, a number/phone/file control, or a range slider — swaps its resting **tonal border** (a darker shade of its own fill) to the **`brand`** edge under a **soft brand ring** the moment it is active/focused, and drops the browser's default outline. A **composite shell** (a bordered wrapper around a quietly outlined inner `<input>`, e.g. an icon search field or the dashboard search) puts the focus state on the **wrapper via `:focus-within`**, never a ring around the inner input alone; a **standalone input** lights up on its own `:focus-visible`; a **range slider** rings its thumb, not the whole track. This is the single, consistent focus signal across every page — marketing, storefront, and dashboard. See `input-field.md`.
- **Every ordinary content section uses `#FFFFFF` with square corners.** Every white section always keeps 48px of left and right inner padding. On marketing and storefront pages, every third section uses the next centered 1280px accent surface in the sequence `#E6DAFE`, `#FFF1BF`, `#C1EEEF`, `#FFE5F4` and takes exactly 24px corners. The component-library page is the explicit exception: every category section remains white and square. Never use dark sections, gradients, grain, or full-width accent color. On marketing, storefront, and component-library pages, the shared page shell owns one uninterrupted subtle border on the left and right from navbar through footer; horizontal section seams use one shared full-viewport 1px `default-subtle` rule and never stack a bottom edge with the next top edge. Dashboards are exempt from the page-side rails.
- **Every navbar, hero, page header, and footer stays solid white.** Use `#FFFFFF` with deep charcoal headings, calm gray body text, deep slate brand actions, and subtle dividers across marketing, storefront, application/dashboard, and component-library pages. These surfaces never inherit a section accent, dark treatment, gradient, pattern, or translucent tint. The scheduled pale accent belongs only to eligible later content sections.
- **Display headings use solid color.** Marketing headings use solid `heading` (`#262626`), semibold 600, gently tightened tracking, and no gradient or clipping effect.
- **Hero decoration stays quiet.** If a dot pattern is used, keep it within a pale contained visual at low contrast and fade it before the edges; never place a high-contrast texture behind reading text.
- **Mockup framing uses quiet depth.** Use a borderless pale outer mat with an explicit 16px radius and 8px padding; the borderless inner solid white image surface also uses an explicit 16px radius and `elevation-2`. Surface contrast and depth define the layers, never an outer stroke.
- **Mockup spacing.** When a mockup or visual (screenshot, app preview, product shot, device frame, illustration) is stacked with text above or below it, leave **~52px** between the mockup and the adjacent content — both above and below — so the visual reads as its own block and never crams against the copy.
- **Prohibited sections are binding.** Each module closes with hard constraints — treat them as such, not as suggestions.

## Canonical vs. summary files

Some installs ship two layers:

| Layer                 | Where                                                             | Use for                                                                                      |
| --------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Canonical modules** | This directory (`colors.md`, `buttons.md`, …)                     | Full anatomy, tokens, states, accessibility, and prohibited rules — read before implementing |
| **Summary stubs**     | Optional nested skill folder (e.g. `.agents/skills/`, `.cursor/`) | Quick orientation and links into the canonical modules                                       |

Summaries are indexes, not substitutes. If a stub and a module ever disagree — on a color, a size, a variant, anything — **the module in this directory wins.**
