## What Blackout is

Blackout is a **polished, production-grade component system** expressed as implementation-agnostic design tokens. Its character is dark, technical, and cinematic: one near-black indigo canvas, translucent lavender hierarchy, square instrument-panel geometry, sparse registration marks, disciplined grid linework, and restrained cyan, orange, pink, and violet state accents. Lausanne is the only type family across headings, body copy, controls, metadata, code, charts, and technical labels. Spacious symmetric sections contrast with compact, precise controls.

### Signature traits — non-negotiable

These are what make a screen recognizably Blackout. Hold every one of them, on every surface:

- **Square instrument-panel geometry** (`radius.md`) — buttons, fields, cards, widgets, tables, overlays, rows, tabs, groups, tooltips, textareas, images, and media resolve to 0px. Only functionally circular controls use `radius-full`.
- **Functionally round controls** — toggle tracks, avatars, radios, range thumbs, status dots, and spinners stay fully round with `radius-full`.
- **One-family Lausanne typography** — headings use medium 500 with tight tracking, body copy uses light 300 at a 15px baseline, and technical labels use the same family with uppercase casing, wider tracking, and tabular numerals. Buttons remain sentence case. Never introduce a serif, monospace, display, or code-specific typeface.
- **One continuous dark page family** — viewport, navbar, hero, sections, application workspace, component library, and footer use `neutral-primary-soft`. Do not alternate section fills.
- **Aligned technical structure** — the shared outer container caps at 1280px. Hero, content-section, and footer interiors keep a 48px gutter from its structural rails, stepping to 24px on tablets and 16px on phones; navbar, dashboard, and nested component containers retain their own canonical padding and are never widened or narrowed by the section gutter rule. One continuous page-shell grid carries shared vertical rails from the first content band through the footer; decorative horizontal background repetition is forbidden, while real section and component seams remain. Ordinary sections stay transparent over the field. Page rails and section seams keep their existing 1px edge tokens; every small plus registration mark uses the dedicated `registration-mark` value (`#272747CC`) in two 1px strokes. Each seam has one owner.
- **Detached corner brackets are forbidden.** Never place an isolated L-shaped crop mark, right-angle corner tick, viewfinder bracket, or partial corner stroke on a page shell, hero, section, navbar, footer, card, control, media frame, or mockup. A real component uses its complete 1px edge; the only permitted registration decoration is the documented small plus at a genuine rail, seam, card corner, or joined-panel intersection.
- **One canonical logo everywhere.** Blackout uses one shared logo component in every navbar, application sidebar or top bar, storefront header, page-system header, and footer. The mark is a complete 32px framed tile containing the same custom linear B glyph and signal dot, followed by the same title-case Blackout wordmark. Never substitute a plain letter tile, chart icon, generic app glyph, text-only wordmark, recolored alternate, or locally redrawn SVG. Context may change surrounding spacing only; mark geometry, wordmark, size, color assignment, and source remain identical.
- **Flat dark surfaces with selective inset light** — cards use a nearby dark or translucent surface, square corners, 24px content padding, a single 1px `default` edge, and `elevation-none`. Floating menus use the overlay elevation scale; selected technical panels may use restrained `elevation-1` inset light. Bright outer glows and ordinary card shadows are forbidden.

## How to use this skill

1. **Load the foundation first.** For any UI work, read `colors.md`, `typography.md`, `spacing.md`, `radius.md`, `shadows.md`, `motion.md`, and `responsive.md` before anything else — every component depends on them.
2. **Add a module per element on the page.** A modal form with inputs and buttons means `modal.md` + `input-field.md` + `buttons.md`. Don't write implementation until the relevant specs are loaded.
3. **Cross-reference.** Components inherit from each other — a search bar satisfies the search section in `input-field.md`; a table footer pulls in `pagination.md`.
4. **Trust these files over memory or external docs.** When this skill and any external or vendor documentation disagree, this skill wins.

## Operating rules

- **No em-dash / en-dash in UI copy.** Never use `—` or `–` in any string the user reads (headings, body, labels, buttons, microcopy); rewrite with a comma, period, colon, or parentheses. Hyphens only inside compound words. See `typography.md`.
- **Outline and primary buttons are the same height.** A button's height is identical whether it is **primary or outline** — the border sits _inside_ the box (`box-sizing: border-box`) and **never adds height**, so the two variants align pixel-for-pixel in a row. See `buttons.md`.
- **Button labels never hide on small screens.** A labeled button keeps its visible text at **every** breakpoint — never collapse "New run" into a bare `+` icon on mobile. When a row runs out of space, adapt the layout instead: wrap, stack, go full-width, or drop/relocate a whole lower-priority control into an overflow menu. Only controls _designed_ icon-only at all sizes (bell, hamburger, close ✕, theme toggle — always with an accessible name) are exempt. Hiding a label with `display: none` inside a breakpoint is prohibited. See `buttons.md`.
- **A designated two-button row is one non-wrapping unit.** When exactly two related landing-page actions are presented as a paired row, they remain beside each other on one line at every viewport, keep the same context tier and height, retain both visible labels, and use one consistent gap. On the narrowest screens, shorten the labels first; if more room is still required, reduce only the pair's inline padding while preserving the documented height, type, icon, and touch target. Never let one button wrap below the other or allow either label to break onto two lines. See `buttons.md` and `responsive.md`.
- **Use the two-tier button hierarchy by context.** Landing-page content uses **Base: 42px high with 24px inline padding**. Application and dashboard actions, navbar and footer actions, and microcomponents use **Small: 36px high with 18px inline padding**; Small icon-only controls are 36 × 36px. The legacy Large alias resolves to Base. Labels use the Lausanne-led UI family at `font-weight-medium` (400), 14px, sentence case, and every standard button uses the 0px `radius-none` corner.
- **Tokens are the vocabulary, and they are implementation-agnostic.** Use semantic tokens such as `neutral-primary-soft`, `heading`, `spacing-4`, `radius-xl`, and `elevation-none` without renaming them.
- **Hold the signature radius.** Every non-circular component token resolves to 0px. Cards, widgets, overlays, menus, tabs, groups, tooltips, fields, selects, alerts, badges, textareas, images, sections, heroes, and footer bands are square. Only intrinsically circular controls and indicators use `radius-full`: radios, toggle tracks and thumbs, avatars, range thumbs, status dots, and spinners.
- **Dark, flat panels; one canonical hairline.** Every card uses a nearby dark or translucent surface, an explicit 0px radius, `spacing-6` (24px) content padding, a visible 1px `default` edge, and `elevation-none`, regardless of viewport or card variant. Composite and edge-to-edge media cards move the same 24px inset to their content cells or body region so the outer frame is not padded twice. Controls and internal seams use that exact same `default` edge; focus adds a separate brand ring without recoloring it.
- **Every component border is the same quiet 1px hairline.** Outer component edges, control outlines, table/card borders, internal dividers, joined-control seams, active-tab indicators, alert and badge borders, and decorative component keylines use `default` at exactly 1px and 80% alpha. Page-shell vertical lines, centered-container rails, and horizontal section seams use the quieter `muted` value at 45% alpha; decorative plus registration marks use `registration-mark` (`#272747CC`). Do not add element opacity to these tokens. No visible border or registration stroke may be 2px or thicker. Accessible focus rings remain separate `box-shadow`/outline indicators and do not change the physical border.
- **One dark page; lavender is the brand family.** Navbar, top bar, hero, page header, ordinary section, workspace, and footer all use `neutral-primary-soft`. `brand` leads focus and compact technical emphasis, while `fg-brand` carries readable links. Cyan, orange, pink, and purple remain semantic or data accents rather than substitute brand fills.
- **The footer is one flat surface.** All footer bands continue the dark page canvas and use only subtle 1px internal dividers; a low-contrast structural grid may continue behind the footer, but gradients and a second footer tint are forbidden.
- **Equal vertical breathing room between sections.** Every section carries the **same spacing above and below it** — the top padding/margin of a section equals its bottom padding/margin, and the gap between any two adjacent sections is symmetric. And the **spacing between any two adjacent sections is identical the whole way down the page**: one uniform vertical rhythm from the first section to the last — a section never introduces a custom, larger, or smaller gap than its neighbours. No section gets more air on one side than the other; rhythm comes from this consistent, balanced spacing, never from uneven gaps. See `spacing.md`.
- **Section vertical padding is 96px, top and bottom.** Every content section uses equal `spacing-24` (96px) padding on large screens and equal `spacing-12` (48px) padding below 768px. This symmetric value stays consistent from the first section to the last.
- **Footer spacing is balanced.** Use 96px top and bottom on large screens and 48px top and bottom below 768px, unless a final legal row owns the bottom inset; in that case subtract that inset from the outer footer so the visible spacing remains balanced.
- **Footer dividers follow the page seam system.** The footer begins with one full-width 1px `muted` seam and the same registration marks used by content sections. Inside the footer, only the final legal or copyright row receives one 1px `muted` top divider; CTA, sitemap, contact, and newsletter groups rely on spacing and must not introduce additional horizontal rules.
- **If the footer's last band already carries its own bottom padding, the footer container drops its bottom padding entirely (never double it).** When the final row of the footer — the bottom bar / copyright band, or whatever sits last — already has its **own `padding-bottom`** (e.g. a bottom bar with `padding-block`), the **outer footer container must set its own `padding-bottom` to `0`** so the two don't stack into an oversized gap. Only **one** element owns the footer's bottom spacing: either the container pads the bottom **or** the last band does — never both. So a bottom bar with, say, `spacing-8` of block padding means the container's bottom padding is `0` (the top padding still follows the 96/112px rule above). If the last band has **no** bottom padding of its own, then the container supplies the light bottom padding from the rule above. Audit the real rendered footer: if you see a large empty band below the last row of content, it is almost always this doubled padding — zero one of the two.
- **Foundation values are law.** Never invent a color, size, radius, or shadow that contradicts the foundation files — if no token fits, the foundation file is where a new one gets added.
- **Closed intent families apply only to alert and badge fills and content.** Brand/info uses `fg-brand-strong`, success uses `fg-success-strong`, danger uses `fg-danger-strong`, and warning uses `fg-warning`; every alert and badge border still uses the canonical 1px `default` edge. A default alert is a compact, content-height row with `spacing-3` block padding, `spacing-4` inline padding, and its leading icon, message block, and visible 20 × 20px dismiss control vertically centered on one axis; never force the dismiss control to the standard 36px button box or give the alert a fixed/minimum height. Do not propagate the intent-family rule to cards, panels, mockup screens, navigation, pagination, tabs, segmented controls, or buttons. Cards always remain dark with normal `heading` and `body` content; primary and status actions use `heading` labels on their translucent intent surface.
- **Every interactive element earns its states.** Hover, focus, and disabled are defined in each module; the brand focus ring is never removed without an accessible equivalent.
- **Button-shaped controls use flat blue-tinted glass, with one app-badge exception.** Primary and leading hero actions use translucent `brand-soft`; Secondary, Outline, Ghost, icon, provider, pagination, segmented, joined-search, and semantic actions use translucent `brand-softer`. Use the shared 14px backdrop blur with 135% saturation so page detail reads faintly through every ordinary button face. Every ordinary contained button uses `elevation-none`, no shadow, and the identical 1px `default` edge. The sole exception is the paired app-distribution badge row in the canonical centered marketing hero: both large store badges use a solid `brand` surface, dark high-contrast content, and no blur or shadow at every breakpoint. Link is the only borderless unpainted action.
- **Translucent informational surfaces always blur what sits behind them.** Low-alpha alerts, badges, pills, chips, compact tinted icon wells, and comparable passive callouts use an 18px backdrop blur with 135% saturation so background gridwork and content cannot remain sharply legible through the component. Opaque neutral variants need no blur. This treatment never adds a shadow, changes the 1px edge, or applies to solid app-distribution badges.
- **Dark-surface CTAs use only Primary Brand or Secondary.** On a dark page surface or inside a dark card, the single leading CTA uses Primary Brand and supporting CTAs use Secondary. Outline, Ghost, and Link are reserved for explicit component demonstrations and specialized utility contexts, not ordinary dark-surface page/card actions. Every ecommerce product-card purchase or add-to-cart action is Primary Brand on its dark card.
- **Dark cards are neutral control boundaries.** Buttons, inputs, selects, textareas, and other controls inside a dark card always use their canonical Blackout background, border, foreground, hover, active, and focus tokens. Accent families belong to state, data, and compact emphasis, not broad panel recoloring. Content actions retain Base geometry while navbar, ecommerce toolbar, pagination, and footer actions retain Small geometry.
- **Semantic HTML, always.** Proper `h1`→`h6` order, `<button>` for actions, `<a>` for navigation, real labels on form controls, and ARIA where a module calls for it.
- **No vendor leakage.** Describe and implement through tokens; never paste vendor-specific implementation strings from external docs into the work.
- **Form controls share one shell.** Text-like controls (`input-field`, `select`, `textarea`, …) inherit the field shell in `input-field.md` unless a module explicitly overrides it.
- **Themed form controls.** Checkboxes, radios, and toggles always render in **this theme's own style** — a `dark-strong` (`#000008`) resting background, a dark translucent `brand-soft` surface for checked checkbox and on-toggle states, a visible `brand` radio dot, plus the theme's border, radius, and focus-ring tokens — never the native/unstyled browser control and never another theme's colors. Resting and active boxes/tracks stay dark; state is carried by the light check, brand dot, white thumb position, and restrained blue tint rather than a bright solid fill. **Reset the native input** (the platform appearance reset) and draw the control yourself — a native `accent-color` tint alone is **not** enough, it still renders the OS control: build the box / track, the checked tint, the check / dot / thumb mark, and the focus ring from this theme's tokens. See `checkbox.md`, `radio.md`, `toggle.md`.
- **Radio inputs are always true circles.** Every default radio uses an equal 18 × 18px `radius-full` well in every state, distinct from the 16 × 16px square checkbox. Its selected state uses a dark translucent `brand-soft` well with a precisely centered 6 × 6px `brand-light` dot; focus adds a separate soft outer halo without changing the 1px edge.
- **Coherent outline icons.** Use one product-supplied outline icon set throughout, sized and colored with tokens; avoid emoji, mixed icon styles, or one-off drawings.
- **Production charts use the dedicated five-color series palette.** Bind dashboard data to a real charting component and assign visible series in the fixed `chart-1` → `chart-2` → `chart-3` → `chart-4` → `chart-5` order. Keep these tokens exclusive to charts, preserve the mapping in legends and tooltips, and never substitute brand, section, or status colors for categorical series. Do not use static images or placeholder bars.
- **In-palette imagery — no bare-icon placeholders.** Product media, carousel slides, mockups, and decorative visuals use artwork composed from the Blackout token palette: dark indigo fields, restrained lavender circuitry, sparse cyan or violet data light, and low-contrast grid detail. **Images and illustrations never carry an outer border** on either the artwork or media wrapper. Internal strokes may describe objects but never frame the illustration. Every media frame uses explicit square corners and clips overflow. Artwork fills its frame edge to edge and never collapses to one generic icon on a tile. User-supplied brand assets are served exactly as provided. Functionally circular avatars remain the documented exception.
- **Spacing comes from the fundamentals.** Take every margin, padding, and gap from the scale in `spacing.md` (never ad-hoc px). Always give **headings and paragraphs room above and below**, and **pad both sides of any border, separator, or divider** so content never crowds a rule. See `spacing.md` and `typography.md`.
- **Every semantic list owns 24px above and below.** Every `ul` and `ol`, on every page and inside every component, uses `spacing-6` (24px) for both `margin-top` and `margin-bottom`. This is fixed across breakpoints and list variants. The list itself owns those two margins; surrounding wrappers must not add another vertical margin that doubles the gap. List indentation and item gaps remain controlled separately.
- **Marketing and storefront navigation uses one fixed square glass bar.** Center the navbar at the top of the viewport, cap it at 1280px, and glue its top edge to the viewport at 0px on every breakpoint; no top margin or floating offset is allowed. Inset it 16px from the viewport sides only when space is tight. It uses the system's square 0px geometry, a translucent blue-indigo page-family surface with backdrop blur and saturation, one 1px `default` edge, and no inner or outer shadow. The bar stays above hero copy and artwork without reading as a detached pill or floating card. Application/dashboard and component-library top bars retain their documented product-shell treatment.
- **Marketing navbar CTA hierarchy.** The marketing navbar's “Get started” action uses the documented Secondary treatment at the Small 36px navbar size. Reserve the Primary Base-size treatment for the hero's leading CTA.
- **The centered app marketing hero has one fixed composition.** Center a responsive two-line heading, a constrained lead, two large solid-`brand` app-distribution badges, one premium portrait phone, and the avatar-plus-rating proof row in that order. The proof cluster uses distinct photographic customer portraits cropped edge-to-edge inside circular avatar rings; never substitute initials, generic glyphs, or repeated faces when portrait assets are available. The store badges are the only solid-brand button exception and use dark content; every other hero action follows the glass hierarchy. The phone uses a thick rounded dark bezel, rounded clipped screen, short side controls, and restrained external depth. See `buttons.md`.
- **Navbar & footer links are text links, not buttons.** A link in the navbar or footer has **no padding and no background/fill hover** — it is **not** a ghost button. On hover it only **lightens its text color** (a subtle lighter/dimmer text tone) because it is a link, not a button. Footer language and locale selectors follow this exact text-link treatment even when accompanied by a globe or chevron; they never inherit button fill, border, glass, or shadow styles. Reserve padded, background-hover treatments for real buttons and sidebar nav items. Adjacent nav links sit **24px** apart.
- **Section width: max 1280px, centered.** Every section, navbar, and footer aligns to one centered 1280px outer container. Apply the 48px inner gutter to hero, content-section, and footer interiors, stepping to 24px on tablets and 16px on phones; do not apply it globally to navbar, dashboard, or nested component containers. Marketing, storefront, and component-library pages align sparse vertical rails and registration marks to this grid. Container rails and section seams use one 1px `muted` structural hairline with exactly one owner; registration plus marks use two 1px `registration-mark` strokes. Do not draw extra side borders around individual sections.
- **Blackout content surface.** Sections, hero, and footer continue one `neutral-primary-soft` canvas around the centered 1280px content container. Variation comes from aligned grid linework, compact panels, technical imagery, and registered accents, never scheduled alternate section fills.
- **Section header → content gap: 48px on large screens.** The **section heading block** — the section heading, plus any lead paragraph and/or buttons that belong with it — is separated from the **rest of the section's content** by a **48px**. Keep the heading, its paragraph, and its CTA buttons together as one intro block (their own internal gaps follow `typography.md` / `spacing.md`), then leave **48px** below that whole block before the body content begins. **Below the `sm` breakpoint (768px) this header → content gap steps down to 32px** — the one responsive step, applied equally on every section.
- **Section header max-width: 768px.** A section header — made up of any combination of an eyebrow, a heading, a supporting paragraph, and/or buttons (whichever the section uses) — is capped at **768px** wide (centered for centered headers, left-aligned within that measure otherwise) so the heading and lead wrap to a comfortable line length instead of stretching the full section width.
- **A section header is one aligned composition.** Use 12px from eyebrow to heading and 24px from heading to supporting copy. For a centered header, center the entire stack — eyebrow, heading, lead, and actions — inside the same measure; never center only the heading while leaving its related copy on the left. For a left-aligned header, every item shares the same left edge.
- **No decorative dashes or numbering in copy.** Never trail a word or label with a dangling dash flourish (e.g. `platform —`), and never number eyebrows, section labels, steps, or list items with zero-padded or hashed sequences (`01`, `02`, `#1`, `#2`). Eyebrows and headings are plain words: no dash "lines", no decorative counters.
- **No accidental duplicate borders inside components.** Where stacked cards, rows, widgets, list items, or adjacent sections share an edge, exactly one element draws that internal border. Never stack a section bottom edge with the following section top edge.
- **Full-width section boundaries are mandatory and never doubled.** Every content section, including the hero, is visually bounded by the same 1px `muted` rule across the full viewport width. Adjacent regions share one rule: each section paints only its top edge, while the first section suppresses that edge when the preceding navbar or band already owns the seam. Never render both sides of one seam, stack two 1px rules, or allow a 2px boundary. Rules stay full-width when a colored surface is capped at 1280px.
- **Input focus encloses the complete shell.** On focus, a field keeps its 1px `default` border and adds a soft brand ring around the full outer wrapper. Composite inputs apply this with focus-within on the wrapper, never around the editable text region alone.
- **Chart tooltips are square data cards.** A chart tooltip is a multi-row data surface, not a pill label: its dark shell uses an explicit 0px radius, `elevation-2`, and one visible 1px `default-subtle` edge. Internal row separators remain `default-subtle`. Each row uses the exact series color on its swatch while label and value use readable `heading` text.
- **Button groups use one gray state surface and own each edge once.** A fused button or segmented-control group uses one dark `neutral-primary-soft` shell with one 1px `default` perimeter edge. Segments have no individual perimeter borders and stay dark at rest; only each segment after the first draws one 1px `default` start-edge divider. Hover, press, and selected states use only `neutral-secondary-soft` with `fg-brand-strong` text/icons. The perimeter and dividers never recolor, and no underline, bottom rule, inset line, shadow, gradient, or additional border may indicate state. Focus adds only the standard focus ring. Never overlap bordered segments or allow adjacent cells to produce a doubled seam.
- **Button type & icon sizes.** Every button label is **14px** and every shaped-control icon is **16px**. Base and Small differ only in box height and inline padding; family, label size, weight, icon size, radius, and states stay identical. The **gap between a button's icon and its label is 6px**.
- **One font and one weight on EVERY button-shaped control — button groups and segmented controls included.** Every button and every button-shaped control renders in the **exact same font family (the UI sans) and the same weight (`font-weight-semibold`, 600)**, at the one **14px** label size, sentence case, normal tracking. Button groups, segmented controls, dropdown triggers, pagination, pills, and tabs are microcomponents and therefore use Small geometry. See `buttons.md`.
- **Button tier placement is binding.** Landing-page hero, section, card CTA, and content actions use Base. Application/dashboard actions, navbar and footer actions, dialogs, drawers, dropdown actions, and every microcomponent use Small. Large is a compatibility alias for Base; no third size is introduced.
- **Button variants are identical inside every dark card.** Primary uses translucent `brand-soft`; Secondary, Outline, Ghost, icon, and semantic buttons use translucent `brand-softer`; only Link stays unpainted. Every button-shaped control uses the same quiet 1px `default` edge, square radius, medium label, glass backdrop treatment, `elevation-none`, and documented hover/focus behavior.
- **Adjacent controls share the tier required by their context.** A landing-page content row uses Base throughout. A dashboard, navbar, footer, dialog, drawer, or microcomponent row uses Small throughout. Never mix 42px Base and 36px Small controls in one row; dropdown/select triggers and paired fields match the surrounding button tier. See `buttons.md` and `dropdowns.md`.
- **Landing-page check lists.** A list whose items lead with a **check icon** (feature ticks, plan inclusions, CTA reassurances) always renders the icon at **16px**, with a **16px gap** between the icon and the text, and the item text at **font-weight-medium (500)**. A bare check uses `heading`; a check inside a pale colored shape uses the darker foreground derived from that shape's own hue.
- **No decorative index numbers on landing pages.** It is **strictly forbidden** to prefix feature cards, steps, benefits, or any list item with a zero-padded ordinal (`01`, `02`, `03`) or any decorative counter on marketing / landing surfaces. Let the heading and copy carry the order and hierarchy — never a numbered badge, eyebrow, or "step 01" label. (Genuine data — a real count, a price, a stat value — is not a decorative index and is fine.)
- **Icon sizing and landing-page color.** An **18px icon is reserved for extra-large** contexts only; default UI icons stay smaller (≈14–16px). **Breadcrumb icons are ≤ 14px.** Always use the outline style (see the icon-library rule). Only standalone decorative, feature, checklist, contact, and store pictogram icons on a landing page use `heading`, never `brand` or `fg-brand`. An icon inside a button, link, alert, badge, tab, field, menu item, or any other labeled component inherits that component's exact text color in every state. The one size exception is the bare marketing pictogram: on landing-page feature and stat blocks, an icon that sits directly on the surface with no shape behind it renders at 36px in `heading`, with a fixed 16px gap between the icon and the text beneath it.
- **Shaped icons use the foreground of their own intent family.** A compact tinted icon tile uses its registered intent foreground and edge; a dark neutral tile uses `heading`. Keep icon tiles square through the 0px component radius and low contrast.
- **Table icons are 16px, never larger.** Any icon placed **inside a table** — a data table or a pricing / comparison table — is capped at **16px** (a `check` / `minus` / `x` cell mark, a sort caret, a row-action glyph, an inline status icon, etc.). Never let a table icon grow past 16px; if it sits in a tinted "chip" (e.g. a success circle behind a check), it may go **smaller** (~14px) so the icon reads comfortably inside its container, but 16px is the hard ceiling.
- **Dropdown panel border & shadow.** Every dropdown / menu panel carries the same 1px `default` border as every other component plus a medium drop shadow so the menu lifts cleanly off the page.
- **Dropdowns and popovers use square corners throughout.** Floating panel, menu items, option rows, and triggers all use the 0px component radius on desktop and mobile.
- **Dropdown menus never scroll by default.** A dropdown / menu panel shows **all of its content at once** — no internal scrollbar, no capped `max-height`, no `overflow: auto/scroll`. Every item is visible and the panel grows to fit its items. Add a scroll area **only when the prompt explicitly asks for it** (e.g. a long searchable list); absent that instruction, never clip or scroll the menu. The panel always carries the **medium shadow** (see the dropdown panel rule above).
- **One hover background for every link surface.** Wherever a link or menu item shows a **background on hover** — top-nav links, sidebar links, dropdown / menu items, command-palette rows, tab-style links — it uses the **same single hover-background tint** (one subtle neutral fill), so the hover feedback is identical across navbars, sidebars, and dropdowns. Choose one value for this and reuse it everywhere — never give the sidebar one hover colour and the dropdown another. The **active / selected** state is a separate, stronger background (a brand tint), likewise reused consistently across all of these surfaces.
- **Selected table rows use the neutral hover background, not a brand tint.** A selected row takes the **same subtle neutral background a row shows on hover**, never a violet brand-tinted fill. A row that is both **selected and hovered stays that exact same colour** (no deepening, no shift). Selection is signalled by the row's checkbox / control state, not by recolouring the row.
- **Textarea corners stay square.** A textarea and its composite wrapper use the same 0px corner as single-line fields.
- **Application widget grid gap is 16px.** On application / dashboard pages, the gap between widgets in the layout grid — both the row and column gutters between cards/widgets — is **16px**.
- **Widgets in the same grid row share the tallest widget's height — set a floor, never a fixed height.** A widget that needs a canvas (a chart, a gauge, a map) declares **`min-height`**, never `height`. A fixed height *locks* the widget, so when a taller sibling sits beside it in the same row the short one refuses to stretch and leaves a dead gap under its content, while the row's own height is set by the tall one anyway. With `min-height` the widget keeps a readable floor and still stretches to the row, and its chart area (the `flex: 1` fill) grows into the extra space. Widgets in a row are always flush top **and** bottom.
- **Widgets never carry their own outer margin — the container's `gap` owns the vertical rhythm.** The dashboard's widget column is a single flex/grid container with **one** `gap: 16px`; every widget and widget-row is a child of it. A widget must not add `margin-bottom` "to space itself", because the moment one widget does and its neighbour doesn't, the rhythm silently breaks (a standalone widget lands flush against the next with a 0px gap while gridded rows keep theirs). **One spacing source, no exceptions.**
- **A height-constrained scroll column must not squash its children.** When the dashboard's main column is a flex column with a constrained height and `overflow-y: auto`, its children inherit `flex-shrink: 1` — so the browser will **shrink every widget to fit the box instead of letting them overflow and scroll**. Tall widgets collapse (a data table crushes to a strip and, if it clips its own overflow, vanishes entirely). Pin the children: **`> * { flex-shrink: 0 }`**, so the column scrolls instead of crushing its content.
- **A scroll container must be a containing block.** Any element with `overflow: auto/scroll` also needs **`position: relative`**. Otherwise an absolutely-positioned descendant with no positioned ancestor (a visually-hidden input, an sr-only label, a decorative layer) anchors to the *initial containing block*, **escapes the scroll container entirely**, and stretches the document — producing a phantom second scrollbar and a long run of dead space below the page. The shell fits the viewport, yet `<html>` scrolls: that is always this bug.
- **Hero H1: up to 64px, 1024px max-width.** The hero's `h1` is the largest type on the page — **64px** on large screens (it may scale down only on narrow mobile viewports for fit). **The one exception is the storefront search hero** (display title + joined search group + deal carousel sharing the brand band): its title runs a fluid **36px → 60px** so the search group and carousel fit the band comfortably — it stays the largest type on the storefront page. Its text wraps within a **1024px** max-width so a long headline breaks onto a tight, readable column instead of running full-width. The **H1 carries a 24px `margin-bottom`**, which sets the gap down to the supporting paragraph. The supporting paragraph (hero lead) that follows the H1 is **20px** on large screens and scales **smaller on mobile** (≈16–18px), and it **also carries a 24px `margin-bottom`** — separating it from the CTAs / content below. The 24px on the H1 already provides the gap above the paragraph, so the paragraph takes **no separate top margin** (never stack a second gap on top of the H1's 44px).
- **Every non-hero page and section heading matches “Why us?”.** Use the same fluid **24px → 36px** size and **medium 500** weight for marketing/storefront section headings, application page titles, and component-library category headings. The hero H1 is the only page-heading exception. Do not promote card, widget, modal, alert, or footer titles to this role; they keep their smaller component typography.
- **One element owns the vertical padding — never two nested.** When a band, card, or CTA sits inside a section, **only one of them adds vertical padding**. A section and an inner band must not both pad top/bottom, or the block bloats and reads off-center. Decide which container owns the vertical rhythm and zero the padding on the other.
- **Newsletter / signup bands get a dedicated layout — not the button-actions slot.** A CTA that holds an **email field + submit button** is a signup row, not a button group: never drop it into a `cta-card__actions` (or any container built for side-by-side buttons). Build a dedicated band — a **two-column grid on desktop** (copy left, form right) with a **hero-style signup row**: a **full-width field shell + Base button, inline from ~640px up and stacked below that**. Give it a responsive title, a `font-size-lg` description, and a small helper line (e.g. "No spam. Unsubscribe anytime.") under the form. **Never a fixed narrow field width** (e.g. 18rem) beside the Base button — the field flexes to fill the row.
- **Reset native element margins inside cards.** Elements the browser margins by default — `<blockquote>`, `<figure>`, `<p>`, `<ul>` / `<ol>` — are set to **`margin: 0`** whenever they are, or sit inside, a card. Otherwise the user-agent's default margin leaks **outside** the card border and reads as phantom padding around the box (a `<blockquote>` testimonial card is the classic trap). All spacing comes from the card's own padding. Also delete dead modifier classes that style nothing (e.g. unused `--1` / `--2` / `--3` variants).
- **Never delete a style rule without proving nothing uses it.** Before removing or "deduplicating" any style, **search the whole codebase for every class / selector it targets** (markup, components, templates, JS) and confirm **zero** references remain. A selector that appears only once in the stylesheet is **not** dead if any element still carries that class — deleting it drops that section to **unstyled HTML**. Deduplicate by **consolidating** repeated declarations into one rule, never by blindly deleting; when in doubt, keep it. After any CSS cleanup, **load the page and confirm every section still renders styled** — then hard-refresh (the dev server may still serve the old CSS bundle).
- **Zero a list's default left padding, not just its margin.** A `<ul>` / `<ol>` used as a layout row, nav, or menu carries the browser's default **~40px left padding** (`padding-inline-start`, reserved for bullets) — `margin: 0` and `list-style: none` do **not** remove it. Explicitly set **`padding: 0`** (or `padding-inline: 0`); if you only set `padding-block`, that left inset stays and the whole row is pushed ~40px inward, misaligning it with the logo / page container. Let the page container own horizontal alignment — the list contributes no indent of its own.
- **Sidebar links use consistent technical states.** Every sidebar nav link uses the same subtle neutral fill on hover and a stronger registered brand tint for active/current state. Both remain square through `radius-md` (0px); active may additionally strengthen text or icon color.
- **Navbar buttons use Small and one weight; no underlines on nav / sidebar links.** Every navbar button uses the 36px Small box, 18px inline padding, and medium 400, 14px label. **Underlined text is never allowed, in any state** (default, hover, focus, active), for **navbar links, navbar buttons, or sidebar links / buttons** — these navigation targets signal interactivity through colour and background, never an underline.
- **Every translucent surface must blur what is behind it.** Any glass panel with a semi-transparent fill pairs that material with backdrop blur, saturation, and an opaque fallback. The fixed marketing/storefront navbar is the canonical blue-indigo glass example; cards and product-shell top bars keep their separately documented surfaces.
- **Badges are always width auto — never full-width.** A badge / tag / chip / status pill sizes to **its own content** (`width: auto`, an `inline-flex` / `inline-block` box that hugs its label + optional icon). It **never stretches to fill its container** — no `width: 100%`, no block/flex that spans the row, no `flex: 1`, no `align-items: stretch` pulling it edge-to-edge. Several badges in a row sit side by side (and wrap) at their natural widths, each only as wide as its text.
- **Pricing card: 24px between the price and the CTA button.** In a pricing card, leave **24px** between the **price line** (e.g. `$249/month`) and the Base CTA button tied to it. Apply it consistently across every card so prices and buttons line up row-to-row.
- **Avatar-only triggers carry no chevron.** In a navbar / top bar, an **avatar shown on its own** (just the photo / initials circle) is itself the trigger — do **not** put a chevron caret beside a bare avatar. A chevron is added **only when the avatar is paired with a visible label** (the person's name / role): `avatar + name → chevron` is fine, `avatar alone → no chevron`. A lone avatar plus a chevron reads as clutter; the avatar is already the affordance.
- **Joined input + button groups square the shared edges.** When an input is **attached to buttons (or addons) on its left and/or right** — a search-with-button, a stepper, a prefix/suffix group, any segmented control where an input touches a button — the **touching edges are squared to `0` radius** so the pieces read as one seamless control. An input with a button on **both sides** has **no border radius at all**; with a button on one side it keeps the theme's radius on the free side and `0` on the joined side. Only the **outer corners of the whole group** carry the theme's normal radius. Critically, the input's **focus border / ring must follow that squared corner too** — never let a rounded corner (or a rounded focus outline) peek out at the seam when the input is focused; the focus state matches the 0-radius joined edge exactly.
- **Card headings are 20px.** A card's heading / title — ecommerce & product cards, feature cards, pricing cards, testimonial and content cards, and cards in general — is **20px**. The **one exception is dashboard / application widgets**: a widget's heading follows the smaller, dense widget-title scale, not this 20px card-title size.
- **Ecommerce navbar collapses to one row on mobile.** On narrow viewports (**< 768px**) the ecommerce header is a **single bar** — logo at the inline start, a **hamburger menu button** at the inline end. The desktop secondary content **collapses off the bar**: the search field, cart / account actions, and the whole category row are **hidden** and move into a **menu panel that opens below the bar** (search + category links + a **"View all categories"** entry). On desktop the full **two-level layout** returns — search + logo + cart / account on the top row, categories on a row beneath. Use the **same hamburger + collapsible-panel pattern as the marketing navbar** so both headers behave consistently.
- **Modals use quiet depth.** A modal uses dark, `radius-xl` (0px), a subtle hairline, `elevation-4`, and a dimming scrim. Internal header and footer rules use `default-subtle`.
- **Heading line-height follows scale.** Display headings use 1.0625 leading; standard headings use 1.1; body copy uses 1.5. Keep headings at medium 500 in the Lausanne-led interface family.
- **Card treatments live in `cards.md`.** Every card uses a nearby dark or translucent surface, square corners, `spacing-6` (24px) content padding, `elevation-none`, and one visible 1px `default` outer edge. Every standalone card carries one quiet `registration-mark` plus at each outer corner; composite cards also mark every true divider-to-perimeter junction, with adjacent cells sharing one mark so symbols never double. Internal seams use the same `default` color. Neither geometry, inset, nor resting elevation changes with viewport, intent, variant, or hover state.
- **No hover glow anywhere.** Cards and tables never glow, change elevation, or track the cursor; table rows use only the documented neutral hover tint.
- **15px body baseline.** Body, paragraph, card copy, and list prose use the 15px Lausanne baseline with 1.5 leading; prominent lead copy may step to 16–20px. Genuine micro-elements and technical metadata use the smaller documented scales. Never shrink reading copy to solve a layout problem.
- **Inline input + button pairs are width-bounded.** Wherever an input sits next to a button in one row — a newsletter signup, sign-in, search, or promo field, in **any section, on a landing page, a dashboard, or inside a card** — the **input is never wider than 400px**, and the **whole group (input + button together) is never narrower than 440px nor wider than 600px**. In practice: clamp the group to a **440–600px** band and cap the input at **≤ 400px** inside it (the button takes the remainder). This keeps the field comfortably sized and the pairing balanced — never a stretched full-width input, never a cramped one. Below the group's min width (narrow mobile), stack the button under the input rather than shrinking either past these bounds.
- **Every input shows a complete focus ring—no exceptions.** Any focusable field—a text/email/password input, textarea, select, search bar, number/phone/file control, or range slider—keeps the canonical 1px `default` border and adds the soft brand ring when active/focused. A **composite shell** (a bordered wrapper around a quietly outlined inner `<input>`, e.g. an icon search field or dashboard search) puts the focus state on the **wrapper via `:focus-within`**, never around the inner input alone; a **standalone input** uses `:focus-visible`; a **range slider** rings its thumb, not the whole track. This is the single consistent focus signal across every page. See `input-field.md`.
- **Input tiers and insets are exact.** Landing-page and footer signup fields use the 42px Base shell with 16px inline padding and 16px text. Navbar, dashboard, toolbar, dialog, drawer, product-option, and other compact fields use the 36px Small shell with 14px inline padding and 14px text. Selects, searches, and composite shells inherit the same tier. Never retain legacy white fills, shadows, oversized 25px insets, or a focus ring on only one inner segment.
- **Toolbar captions stay compact.** Short labels that introduce ecommerce filter groups, sorting controls, seller selectors, or similar dense toolbar options use the 12px technical-label tier at regular weight in `body-subtle`; they never inherit 16px body copy or heading weight.
- **Every ordinary content section continues `neutral-primary-soft` with square corners.** Keep a 48px content gutter inside the 1280px structural rails, stepping to 24px on tablets and 16px on phones. A moderately quiet `muted` structural grid, aligned rails, and sparse registration marks may span section backgrounds; accent color stays inside data, state, focus, or compact technical callouts. Horizontal seams use one shared full-width 1px `muted` rule and never stack adjacent edges.
- **Navbar, hero, page header, and footer share the dark family.** Marketing and storefront navbars use the fixed square blue-indigo glass bar and remain pattern-free; hero, page sections, and footer may continue the registered low-contrast structural grid, with solid `heading`, calm `body`, restrained lavender actions, and subtle dividers. Broad section gradients and alternate section tints are forbidden.
- **Display headings use solid color.** Marketing headings use solid `heading`, medium 500, gently tightened tracking, and no gradient or clipping effect.
- **Hero decoration stays quiet.** Structural square grid linework may sit behind the hero at very low contrast and must fade before it competes with reading text. Dense dots or high-contrast texture behind copy are forbidden.
- **Mockup framing uses quiet technical depth.** Use a borderless dark outer mat with an explicit 0px radius and 8px padding; the inner dark image surface also uses an explicit 0px radius and `elevation-2`. Surface contrast and controlled overlay depth define the layers, never a bright outer stroke.
- **Mockup spacing.** When a mockup or visual (screenshot, app preview, product shot, device frame, illustration) is stacked with text above or below it, leave **~52px** between the mockup and the adjacent content — both above and below — so the visual reads as its own block and never crams against the copy.
- **Prohibited sections are binding.** Each module closes with hard constraints — treat them as such, not as suggestions.

## Canonical vs. summary files

Some installs ship two layers:

| Layer                 | Where                                                             | Use for                                                                                      |
| --------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Canonical modules** | This directory (`colors.md`, `buttons.md`, …)                     | Full anatomy, tokens, states, accessibility, and prohibited rules — read before implementing |
| **Summary stubs**     | Optional nested skill folder (e.g. `.agents/skills/`, `.cursor/`) | Quick orientation and links into the canonical modules                                       |

Summaries are indexes, not substitutes. If a stub and a module ever disagree — on a color, a size, a variant, anything — **the module in this directory wins.**
