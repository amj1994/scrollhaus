# TypeUI · Blueprint — Design System

> **⚠️ READ FIRST — NON-NEGOTIABLE.** Do **not** design, build, or write any component, section, or page until you have **carefully read every `.md` file in this directory**. Read them all first, _then_ consciously decide what to create — only after that may you build components, sections, and pages. There are no exceptions.

> **🚫 NEVER INVENT A SOLUTION — FORBIDDEN.** When a treatment is already defined here (an inverted section, hero, card, control, color, radius, or interaction state), use the documented pattern and token values rather than improvising a new visual system. Search these files and the existing product for the established treatment first. Only create a new treatment after confirming none exists, and compose it from these tokens and rules.

This skill is the **authoritative visual specification for TypeUI "Blueprint"** (from [typeui.sh](https://www.typeui.sh)). Every component, layout, and page follows the bundled modules. They define what Blueprint looks like down to the token while remaining independent of implementation language, rendering system, or application architecture.

**The canonical specs are the `*.md` files in this directory.** Read the full module before you write UI for it. A nested skill folder may ship short summaries; those are wayfinding only and link back to these files.

## What Blueprint is

Blueprint is a **polished, production-grade component system**, expressed as implementation-agnostic design tokens. Its character is architectural, paper-warm, and precise: a permanent brand-blue footer, a brand-blue hero whenever no intentional media is present, one consistent `#F2EAD6` content-section surface, `#F7F1E4` panels, graphite ink, exact blueprint blue `#003488`, and exact drafting coral `#ED6540`. Every standard component uses a 2px corner, with circular full rounding reserved for numeric count badges, radio controls, and range-slider thumbs; exact 1px rules and flat surfaces complete the system, with one restrained shadow reserved for open dropdown panels and chart tooltips.

### Signature traits — non-negotiable

These are what make a screen recognizably Blueprint. Hold every one of them, on every surface:

- **Uniform 2px geometry** (`radius.md`) — every component and surface uses its compatible radius token resolving to 2px: controls, fields, cards, overlays, menus, media frames, indicators, and feature panels alike.
- **Three circular exceptions** (`radius-full`, 9999px) — equal-sided numeric count badges, radio controls, and range-slider thumbs always render as true circles. No other component, control, avatar, dot, pill, or panel uses full rounding.
- **Lato typography throughout, with one strict weight hierarchy.** Only a semantic `h1` uses `font-weight-black` (900; 800 is the permitted fallback when 900 is unavailable). Every `h2`–`h6`, textual link, button, and button-shaped control uses `font-weight-normal` (400). Paragraphs, labels, non-button controls, table text, badges, captions, metadata, values, and every other non-heading text role use `font-weight-light` (300), including `strong` and `b`. The single data-hierarchy exception is an application/dashboard widget's title and primary numeric readout, which use `font-weight-bold` (700); their supporting labels, deltas, legends, and ordinary table copy remain light. Short coordinates and annotations may use `font-family-monospace`, but keep the same 300 non-heading weight. Page reading copy holds a 16px floor. See `typography.md`.
- **Fixed product-page color sequence.** A product-facing hero is `brand` (`#003488`) whenever it has no intentional full-bleed media; an image-backed hero keeps brand underneath its media and overlay. Every intervening content section uses the same `#F2EAD6` background, and the footer's visual panel is always solid brand. The approved framed marketing footer may expose a 24px page-surface gutter around that brand panel; no other footer changes the sequence. The components catalogue is a documentation surface rather than a product hero, so its introductory header continues the same `#F2EAD6` surface as its sections. No alternate section background enters either sequence.
- **Paper components with coral accents** — panels use `#F7F1E4`; coral remains a small secondary accent and never replaces one of the assigned full-width bands. See `colors.md`.
- **One cream-derived neutral family.** Anchor every non-brand, non-semantic surface to the section cream `#F2EAD6`. Cards step lighter to `#F7F1E4`, controls lighter again to `#FBF8F0`, supporting surfaces step darker to `#E8DFC9` / `#E0D5BB`, and structural edges use the darkest cream `#CFC3A5`. Do not introduce unrelated gray, taupe, white, or beige surface shades. Brand blues remain the brand family; success, warning, and danger remain distinct only when they communicate real state.
- **Fine borders and restrained elevation** — every component edge is exactly 1px and every resting component uses `elevation-none`. Nothing glows or increases elevation on hover. The sole depth exceptions are open dropdown panels and chart tooltips using the restrained `elevation-2`; dropdown triggers and items remain flat. See `shadows.md`.

## How to use this skill

1. **Load the foundation first.** For any UI work, read `colors.md`, `typography.md`, `spacing.md`, `radius.md`, `shadows.md`, `motion.md`, and `responsive.md` before anything else — every component depends on them.
2. **Add a module per element on the page.** A modal form with inputs and buttons means `modal.md` + `input-field.md` + `buttons.md`. Do not write implementation code until the relevant specs are loaded.
3. **Cross-reference.** Components inherit from each other — a search bar satisfies the search section in `input-field.md`; a table footer pulls in `pagination.md`.
4. **Trust these files over memory or external docs.** When this skill and any external or vendor documentation disagree, this skill wins.

## Operating rules

- **No em-dash / en-dash in UI copy.** Never use `—` or `–` in any string the user reads (headings, body, labels, buttons, microcopy); rewrite with a comma, period, colon, or parentheses. Hyphens only inside compound words. See `typography.md`.
- **Outline and solid buttons are the same height.** A button's height is identical whether it is **solid or outline** — the border sits _inside_ the box (`box-sizing: border-box`) and **never adds height**, so the two variants align pixel-for-pixel in a row. See `buttons.md`.
- **Button labels never hide on small screens.** A labeled button keeps its visible text at **every** breakpoint — never collapse "New run" into a bare `+` icon on mobile. When a row runs out of space, adapt the layout instead: wrap, stack, go full-width, or drop/relocate a whole lower-priority control into an overflow menu. Only controls _designed_ icon-only at all sizes (bell, hamburger, close ✕, theme toggle — always with an accessible name) are exempt. Hiding a label with `display: none` inside a breakpoint is prohibited. See `buttons.md`.
- **Button tiers have exact outer heights: Small 32px, Base 40px, Large 48px.** Every variant uses `box-sizing: border-box`, a 14px regular 400 sentence-case label, and the same height within its tier. Inline padding is 12px Small, 16px Base, and 20px Large. Borders sit inside the box. Preserve a 44px touch target around compact controls on touch devices. See `buttons.md`.
- **Tokens are the vocabulary, and they are agnostic.** `neutral-primary-soft`, `heading`, `default-medium`, `spacing-4`, `radius-xxl`, and `elevation-none` are Blueprint tokens, not implementation utilities. Map them into the receiving product's existing token layer.
- **Hold the signature radius.** All standard component radius tokens resolve to 2px. `radius-full` is allowed only on an equal-sided numeric count badge, radio control, or range-slider thumb; each must always be circular.
- **Fine borders and flat surfaces.** Every visible component border is exactly 1px. Non-brand controls and surfaces use `#CFC3A5`: cards, widgets, secondary and status buttons, inputs, overlays, menus, status treatments, and internal dividers. Every border placed on a `brand` surface or over a media-backed image uses the translucent `brand-subtle` edge (`rgba(255, 255, 255, 0.16)`): this includes filled `brand` buttons, selected `brand`-filled tabs, hero controls, image-hero navbar rules, and footer dividers. The translucency lets broad structural rules remain quiet over solid blue and photographic detail instead of cutting the surface into opaque bands. A fused input group is the precise exception: its outer field edge and every internal separator between addon, field, and attached button remain the input-tone `#CFC3A5`, even when the group sits on a brand hero or navbar. Border color otherwise remains stable on hover, focus, active, selected, validation, or intent states; keyboard focus uses a separate outline. Components explicitly defined as borderless stay borderless. Components use `elevation-none` and never lift on hover; the only exceptions are open dropdown panels and chart tooltips, which use the restrained `elevation-2` shadow documented below.
- **Footer is always brand blue; a product-facing hero is brand blue unless it has intentional media.** Every footer's visual panel uses `brand` (`#003488`) across its full panel with warm-paper text and exact 1px `brand-subtle` component dividers where a divider is present. The approved image-backed marketing footer may place that panel inside the documented 24px page-surface frame; the panel itself remains fully brand-backed beneath its image and overlay. Every product-facing hero without a photographic or illustrated background also uses solid `brand` (`#003488`). A hero with intentional full-bleed media may show that image, but its underlying fallback color remains `brand` and it carries a dark brand-toned overlay for readable light copy. The components catalogue header is the sole documentation exception and uses `neutral-primary-strong` (`#E8DFC9`), one darker cream step than its `#F2EAD6` sections, with `heading` and `body` text so every palette specimen remains visible.
- **Content sections use one color.** Every section between the hero and footer uses `#F2EAD6`. Do not alternate section colors and do not introduce another full-section fill.
- **Equal vertical breathing room between sections.** Every section carries the **same spacing above and below it** — the top padding/margin of a section equals its bottom padding/margin, and the gap between any two adjacent sections is symmetric. And the **spacing between any two adjacent sections is identical the whole way down the page**: one uniform vertical rhythm from the first section to the last — a section never introduces a custom, larger, or smaller gap than its neighbours. No section gets more air on one side than the other; rhythm comes from this consistent, balanced spacing, never from uneven gaps. See `spacing.md`.
- **Section vertical padding is symmetrical.** Every content section uses `96px` (`spacing-24`) at both top and bottom on wide screens and `64px` (`spacing-16`) at both top and bottom on narrower screens. Colored, paper, pricing, FAQ, and feature sections follow the same rule. Remove child margins that secretly add extra space to one side.
- **Footer vertical padding is symmetrical too.** Use the same top and bottom padding token on the footer's content wrapper. If safe-area accommodation is required, add it outside the visual spacing calculation so the designed rhythm remains equal.
- **One wrapper owns the footer's equal padding.** Internal footer bands do not add outer top or bottom spacing. Put the matching padding pair on one content wrapper, then keep the first and last bands flush inside it so nested padding cannot distort the symmetry.
- **Foundation values are law.** Never invent a color, size, radius, or shadow that contradicts the foundation files — if no token fits, the foundation file is where a new one gets added.
- **Every interactive element earns its states.** Hover, focus, and disabled are defined in each module; the brand focus ring is never removed without an accessible equivalent.
- **Text contrast at every state is non-negotiable.** Label and background must meet WCAG 2.2 AA in default, hover, focus, active, and disabled states. Primary blue takes white; paper uses `heading` (`#0D294E`) or the shared readable body color used by both `body` and `body-subtle` (`#2C3A4B`); coral uses `heading` for normal-size text. Interactive control boundaries and focus indicators must remain clearly perceivable; cards use their quieter documented `buffer` hairline because their surface, spacing, and heading provide the grouping cue. Verify transition frames as well as endpoints.
- **Semantic HTML, always.** Proper `h1`→`h6` order, `<button>` for actions, `<a>` for navigation, real labels on form controls, and ARIA where a module calls for it.
- **No implementation leakage.** Describe and implement through semantic tokens; never paste external class strings or technology-specific naming into the design-system contract.
- **Form controls share one shell.** Text-like controls (`input-field`, `select`, `textarea`, …) inherit the field shell in `input-field.md` unless a module explicitly overrides it.
- **Themed form controls.** Checkboxes, radios, and toggles always render in **this theme's own style** — the theme `brand` fill when checked / selected / on, plus the theme's surface, border, radius, and focus-ring tokens — never the native/unstyled browser control and never another theme's colors. **Reset the native input** (`appearance: none`) and draw the control yourself — a native `accent-color` tint alone is **not** enough, it still renders the OS control: build the box / track, the checked `brand` fill, the check / dot / thumb mark, and the focus ring from this theme's tokens. See `checkbox.md`, `radio.md`, `toggle.md`.
- **Checkbox state changes are paint-only and layout-invariant.** The control remains a fixed 16 × 16px box with one stable inline baseline in unchecked, checked, and indeterminate states. Draw the check or dash as an absolutely positioned layer inside that fixed box; never insert it into inline-grid, flex, or normal flow where toggling one row or selecting an entire table can change intrinsic row height, scroll anchoring, or surrounding widget positions.
- **Selection controls keep distinct geometry.** Checkboxes are 16 × 16px boxes using `radius-xs` (2px). Radios are equal-sided 16 × 16px controls using `radius-full` (9999px), and both their outer control and checked inner mark must remain true circles in every state and context.
- **Use the product's established icon set.** Every UI icon uses the same outlined, technical drawing style and the theme's size and color tokens. Never mix icon families, emoji, or unrelated glyph styles.
- **Use production data visualization.** Dashboard charts bind to real data and use the theme's semantic color, typography, border, and spacing values. Never substitute a static placeholder for required interactive data behavior.
- **In-palette imagery — no arbitrary stock photos or bare-icon placeholders.** Product shots, category media, carousel slides, and every other generated content image render as **placeholder artwork drawn entirely from the theme's own tokens** — a soft light gradient field with a fine low-opacity texture, a framed-photo pictogram (frame, sun, layered hills with a seeded tone variation), small sparkle accents, and caption bars — composed as a real illustration. The artwork **fills its media frame edge to edge** (cover/slice cropping, centered); **never render media as a lone small icon centered on a gray tile**, and **never hotlink third-party photographs**. A user-supplied hero photograph is allowed as intentional full-bleed hero media; keep `brand` as its fallback and add the documented dark brand overlay. User-supplied brand files are served exactly as provided. Decorative section illustrations are likewise in-palette vectors or supplied assets.
- **Spacing comes from the fundamentals.** Take every margin, padding, and gap from the scale in `spacing.md` (never ad-hoc px). Always give **headings and paragraphs room above and below**, and **pad both sides of any border, separator, or divider** so content never crowds a rule. See `spacing.md` and `typography.md`.
- **Hero navbars are part of the hero, never a separate bar.** On both marketing and storefront pages, every navbar tier sits structurally **inside the blue hero band** and uses a fully transparent background over the hero's exact `#003488` surface. It has no tint, translucent fill, backdrop blur, shadow, or bottom border; the hero pattern and blue field continue uninterrupted behind it. Links and icons use the hero's light foreground treatment. **The dashboard / application top bar** keeps its own app-shell treatment because it is not a hero navbar.
- **Framed image bookends use one 24px outer inset.** When the approved image-backed marketing hero or image-backed marketing footer is used, the outer page-surface wrapper applies `spacing-6` (24px) on all four sides and the inner media panel owns the image, overlay, clipping, and `radius-md` (2px) corners. The hero panel fills the remaining small-viewport height (`100svh` minus the 48px combined block inset), with its navbar inside the panel and its copy vertically centered. The matching footer keeps the same 24px frame but sizes from its content; its one inner panel owns equal top and bottom padding. Never apply the frame separately to the navbar, content, or footer bands, and never stack a second container inset inside it.
- **Hero buttons preserve hierarchy.** On a blueprint-blue hero, the primary uses warm paper with blue text and `elevation-none`; the secondary is transparent with a warm-paper label. Both use the exact 1px `brand-subtle` edge required for controls on a brand surface. Do not render every hero action as the same fill treatment. See `buttons.md`.
- **Navbar and footer links keep true text-link anatomy, with a navbar-specific hover.** Plain navbar links remain transparent and never underline; hover is expressed only by shifting the foreground to the navbar's stronger readable text color. Footer, sidebar, prose, table, and ordinary link-list anchors remain transparent and use the documented 1px underline with a 3px offset. Never paint `hover-fill` or any other background behind a plain anchor. Button-shaped anchors, tabs, dropdown rows, pagination controls, and icon controls remain governed by their component state rules. Adjacent nav links sit **24px** apart.
- **One Blueprint logo component across every page.** Marketing, application, components, ecommerce, and every footer use the same logo anatomy and measurements: a 32px square 2px-corner mark, 10px gap, and 18px Lato Regular wordmark. Light surfaces use a `brand` mark with a white glyph and `fg-brand` wordmark; brand or media-overlay surfaces invert the same mark to `neutral-primary` with a `brand` glyph and a white wordmark. Never recreate the logo with page-local markup, initials, kicker dots, altered dimensions, or different typography.
- **Links use one visible brand treatment.** Every textual link on a light surface uses `fg-brand` (`#003488`) at `font-weight-normal` (400), including inline, standalone, navigation, footer-on-light, breadcrumb, table, accordion, and card links. A link on the brand-blue hero, footer, or another dark/inverted surface uses the documented light foreground for contrast while retaining weight 400. Button-styled anchors follow button colors instead of the textual-link color.
- **Section width: max 1280px, centered.** Every section's content sits in a **centered container with a max-width of `1280px`** (equal auto left/right margins). Sections are always horizontally centered — never left/right-aligned or off-center, and never wider than 1280px of content. A full-bleed background may still span the viewport, but the **content is capped at 1280px and centered**. Inside the container, the content **spans the full 1280px on desktop with no side inset** (`padding-inline: 0`) — the centered container's own auto left/right margins hold it clear of the viewport edge. Side padding applies **only on narrower viewports, so content never touches the edge: `40px` (`spacing-10`) below the 1360px breakpoint, and `24px` (`spacing-6`) below 768px**. Every section, the navbar, and the footer share this one container, so all content aligns to a single left and right edge.
- **Blueprint content surface: 1280px centered content.** Marketing and storefront content uses one consistent `#F2EAD6` section surface inside a centered 1280px container. The footer remains solid brand blue; the hero is solid brand unless intentional full-bleed media is present, in which case brand remains the fallback beneath it. A low-contrast static paper texture is allowed if it does not alter the assigned color or interfere with reading.
- **Section header → content gap: at least 64px (margin-bottom).** The **section heading block** — the section heading, plus any lead paragraph and/or buttons that belong with it — is separated from the **rest of the section's content** by a minimum of **64px**. Keep the heading, its paragraph, and its CTA buttons together as one intro block (their own internal gaps follow `typography.md` / `spacing.md`), then leave **≥ 64px** below that whole block before the body content begins. **Below the `sm` breakpoint (768px) this header → content gap steps down to 48px** — the one responsive step, applied equally on every section.
- **Section header max-width: 768px.** A section header — made up of any combination of an eyebrow, a heading, a supporting paragraph, and/or buttons (whichever the section uses) — is capped at **768px** wide (centered for centered headers, left-aligned within that measure otherwise) so the heading and lead wrap to a comfortable line length instead of stretching the full section width.
- **No decorative dashes or numbering in copy.** Never trail a word or label with a dangling dash flourish (e.g. `platform —`), and never number eyebrows, section labels, steps, or list items with zero-padded or hashed sequences (`01`, `02`, `#1`, `#2`). Eyebrows and headings are plain words: no dash "lines", no decorative counters.
- **No duplicate borders between sections.** Where two adjacent sections (or stacked cards, rows, widgets, list items) share an edge, **only one of them draws that border** — never both. If a section has a bottom border, the next section does **not** also add a top border, so the shared line stays a single hairline, never a doubled 2px-thick line. Pick one direction (e.g. bottom-only) and apply it consistently; the last element omits the trailing edge.
- **One barely visible divider at selected marketing content-section boundaries.** Standard marketing boundaries use one centered, uninterrupted, container-width **1px `buffer` hairline** at low opacity that tapers softly to transparent at both ends. A divider is neutral structure, so it never uses brand or accent color. The divider belongs only to the following section's top edge, preventing doubled borders. Omit it between pricing and testimonials so those two related conversion / proof sections flow together. It stays flat with no marker, gap, second rule, or shadow, and never appears between the hero and first section or between internal cards / widgets.
- **Input focus uses the documented brand indicator.** On focus, the field shell retains its `#CFC3A5` border and adds a soft brand outline described in `input-field.md`; the inner input of a composite shell never draws a second ring.
- **Chart labels and tooltips preserve contrast.** A label drawn directly inside a filled pie slice, bar, area, or other solid chart mark always uses `white`, regardless of series colour; labels outside filled marks keep the normal chart-axis or body foreground. Every chart tooltip uses the exact **1px `#CFC3A5` border**, 2px `radius-md`, and restrained `elevation-2` shadow (`0 12px 28px rgba(13, 41, 78, 0.16)`) used by an open dropdown panel. Apply the border and shadow to the tooltip root only. Each tooltip item — its swatch, label, and value — is rendered in **that series' chart colour**, so the tooltip maps 1:1 to the lines/bars it describes.
- **Button type & icon sizes.** Button labels are **14px on every tier**, including Extra small, Small, Base, and Large. Labels use sentence case and 400 weight; tiers differ by exact outer height and inline padding, never by label size. The gap between a button's icon and label is 6px.
- **One font and one weight on EVERY button-shaped control — button groups and segmented controls included.** Every button and button-shaped control — plain buttons, groups, segmented controls, dropdown/select triggers, pagination buttons, pills, and tabs — uses the UI sans at `font-weight-normal` (400), with the documented label size, sentence case, and normal tracking. No control raises its label weight for active, selected, intent, or emphasis states. See `buttons.md`.
- **Button tier placement.** Hero CTA buttons are **Large 48px** by default; buttons in sections, cards, CTA cards, and the footer are **Base 40px**. Every button-shaped control inside a dashboard/application shell is **Small 32px without exception**, including navbar, toolbar, widget, table, tab, pagination, dropdown/select trigger, icon button, modal, and drawer actions. Base and Large are forbidden inside dashboards/applications.
- **Buttons are consistent across sections — same anatomy everywhere.** A given button role looks and behaves identically wherever it appears on a page: a marketing CTA / signup / submit button carries the same variant, height, radius, label weight, brand fill, exact 1px edge, and no shadow in the hero, pricing cards, CTA band, and footer signup. Non-brand buttons keep the 1px `#CFC3A5` edge. **In an input + button pair, the two exact heights match:** Small 32px, Base 40px, or Large 48px. Pair a Base field with a Base button and a Large field with a Large button; never place a Small button beside a Base/Large input. Dashboard/application pairs always use Small 32px on both sides.
- **Adjacent controls in one row share one exact measured height, no exceptions.** Any row of controls sitting side by side, including button + button, button + dropdown/select trigger, button + input, and trigger + icon button, renders every control at the same tier box: **32px Small in every dashboard/application context, 40px Base in page content, or 48px Large only for an intentional hero group**. The input, wrapper, select, button, trigger, and icon button all use `box-sizing: border-box`; borders cannot add height. A dashboard field beside a button is therefore 32px + 32px, never 32px + 40px. Every button-shaped control also shares the 14px, 400, sentence-case label voice. See `buttons.md`, `input-field.md`, and `dropdowns.md`.
- **Landing-page check lists.** A list whose items lead with a **check icon** always renders the icon at **16px in the `brand` color**, with a **16px gap** between the icon and the text, and the item text at `font-weight-light` (300).
- **No decorative index numbers on landing pages.** It is **strictly forbidden** to prefix feature cards, steps, benefits, or any list item with a zero-padded ordinal (`01`, `02`, `03`) or any decorative counter on marketing / landing surfaces. Let the heading and copy carry the order and hierarchy — never a numbered badge, eyebrow, or "step 01" label. (Genuine data — a real count, a price, a stat value — is not a decorative index and is fine.)
- **Icon sizing.** An **18px icon is reserved for extra-large** contexts only; default UI icons stay smaller (≈14–16px). **Breadcrumb icons are ≤ 14px.** Always the outline style (see the icon-library rule). **The one exception is the bare marketing pictogram: on landing-page feature and stat blocks, an icon that sits directly on the surface with no shape behind it (no tile, chip, or icon container) renders at 36px, in the muted gray `body-subtle` (never the brand/ink), with a fixed 16px gap between the icon and the text beneath it** — the icon itself is the visual, so it takes display scale. **On a blue brand band the same bare pictogram keeps the 36px size but renders in soft white (white at ~85% opacity) instead of the gray**, since `body-subtle` is unreadable on the deep blue fill. The moment an icon sits inside a shaped container (an icon tile, button, input, badge, or list chip), it drops back to the standard control sizes above.
- **Marketing icons match their text foreground.** Every icon on a marketing page inherits the exact foreground color of the text or control it belongs to: body icons use `body` or `heading` with their adjacent copy, button icons use the button label color, link icons use the link color, and hero / footer icons use the same light inverted foreground as their text. Do not introduce brand blue only on the glyph when the surrounding text uses another color.
- **Shape icons are a tonal step of their surface.** A glyph inside a **filled tile / icon container** (the FAQ topic icons, the hero feature icons, and the like) is drawn as a **tonal step of the surface it sits on**: the **tile fills a slightly lighter shade of that surface**, and the **glyph a lighter shade again**, so the tile lifts off the surface and the glyph reads clearly on the tile — a quiet, monochromatic stack, never a foreign brand fill. On the blueprint-blue surfaces (the teal FAQ cards, the blue hero) that is a lighter tint of the `#003488` teal: the tile `color-mix(in srgb, teal 85%, #fff)`, the glyph `color-mix(in srgb, teal 50%, #fff)`. The surface, one step lighter for the tile, one step lighter again for the icon.
- **Table icons are 16px, never larger.** Any icon placed **inside a table** — a data table or a pricing / comparison table — is capped at **16px** (a `check` / `minus` / `x` cell mark, a sort caret, a row-action glyph, an inline status icon, etc.). Never let a table icon grow past 16px; if it sits in a tinted "chip" (e.g. a success circle behind a check), it may go **smaller** (~14px) so the icon reads comfortably inside its container, but 16px is the hard ceiling.
- **Every table header label is typographically identical.** Plain and sortable column labels use the same Lato family, 12px size, 400 weight, 1.25 line height, normal casing, letter spacing, and `body-subtle` colour. A sortable header is a table label first and must never inherit the dashboard button size or line height. Sorting state is communicated by its icon and `aria-sort`, not by changing the label typography.
- **Dropdown panel edge, shadow, and row states.** Every dropdown / menu panel carries the universal exact **1px `#CFC3A5` border** plus the restrained dropdown-only `elevation-2` shadow (`0 12px 28px rgba(13, 41, 78, 0.16)`). Apply that shadow directly to the portalled menu node rather than relying on a page ancestor. The trigger, menu items, and pseudo-elements remain shadowless; keyboard focus uses the documented outline only. A selected / active menu row uses the **exact same** `hover-fill` background and `heading` text as hover — never `brand-softer` or another blue selection tint. A dropdown row is a control even when implemented with an anchor, so its label is **never underlined** at rest, hover, focus, active, selected, or visited.
- **Dropdown row icons are bare, semantically direct glyphs.** A leading SVG inside a menu item has no CSS border, background, radius, shadow, or icon tile. Choose the symbol that names the destination most clearly; Billing uses an invoice / receipt-text glyph rather than a generic payment-card icon. An outline that belongs to the glyph drawing is allowed, but never wrap it in an additional component frame.
- **Dropdown menus never scroll by default.** A dropdown / menu panel shows **all of its content at once** — no internal scrollbar, no capped `max-height`, no `overflow: auto/scroll`. Every item is visible and the panel grows to fit its items. Add a scroll area **only when the prompt explicitly asks for it** (e.g. a long searchable list); absent that instruction, never clip or scroll the menu. The panel keeps its exact 1px edge and dropdown-only `elevation-2` shadow.
- **Separate text-link hover from control hover.** Plain textual anchors never paint a hover background. Navbar anchors never underline and use only a foreground-color shift; other plain links keep their foreground stable and add the documented 1px underline with a 3px offset. Button-like surfaces such as ghost and link buttons, dropdown/menu rows, command-palette rows, pagination controls, and inactive tabs use the exact `hover-fill` (`#E0D5BB`) with `heading` (`#0D294E`) text and icons and **never underline their labels**. Never make a plain link look like one of those controls. Semantic danger rows may retain `danger-soft`; selected tabs retain the stronger `brand` background with a `white` label and a 1px `brand-subtle` border. Controls bound to the brand application navbar use the documented tonal-blue exception.
- **Selected table rows use the neutral hover background, not a brand tint.** A selected row takes the **same subtle neutral background a row shows on hover** — never an blue / brand-tinted fill. A row that is both **selected and hovered stays that exact same colour** (no deepening, no shift). Selection is signalled by the row's checkbox / control state, not by recolouring the row.
- **Textarea corners match other fields.** A multi-line field uses `radius-md` (2px), never panel or pill rounding.
- **Application widget grid gap is 16px.** On application / dashboard pages, the gap between widgets in the layout grid — both the row and column gutters between cards/widgets — is **16px**.
- **Widgets in the same grid row share the tallest widget's height — set a floor, never a fixed height.** A widget that needs a canvas (a chart, a gauge, a map) declares **`min-height`**, never `height`. A fixed height *locks* the widget, so when a taller sibling sits beside it in the same row the short one refuses to stretch and leaves a dead gap under its content, while the row's own height is set by the tall one anyway. With `min-height` the widget keeps a readable floor and still stretches to the row, and its chart area (the `flex: 1` fill) grows into the extra space. Widgets in a row are always flush top **and** bottom.
- **Widgets never carry their own outer margin — the container's `gap` owns the vertical rhythm.** The dashboard's widget column is a single flex/grid container with **one** `gap: 16px`; every widget and widget-row is a child of it. A widget must not add `margin-bottom` "to space itself", because the moment one widget does and its neighbour doesn't, the rhythm silently breaks (a standalone widget lands flush against the next with a 0px gap while gridded rows keep theirs). **One spacing source, no exceptions.**
- **A height-constrained scroll column must not squash its children.** When the dashboard's main column is a flex column with a constrained height and `overflow-y: auto`, its children inherit `flex-shrink: 1` — so the browser will **shrink every widget to fit the box instead of letting them overflow and scroll**. Tall widgets collapse (a data table crushes to a strip and, if it clips its own overflow, vanishes entirely). Pin the children: **`> * { flex-shrink: 0 }`**, so the column scrolls instead of crushing its content.
- **A scroll container must be a containing block.** Any element with `overflow: auto/scroll` also needs **`position: relative`**. Otherwise an absolutely-positioned descendant with no positioned ancestor (a visually-hidden input, an sr-only label, a decorative layer) anchors to the *initial containing block*, **escapes the scroll container entirely**, and stretches the document — producing a phantom second scrollbar and a long run of dead space below the page. The shell fits the viewport, yet `<html>` scrolls: that is always this bug.
- **Hero H1: 60–64px, 1024px max-width.** A solid brand product hero uses the 64px display token. The approved framed image-backed marketing hero uses 60px, and the storefront hero may run fluidly from 36px to 60px so its full composition fits; each remains the largest type on its page and may scale down further only on narrow mobile viewports. Hero text wraps within a 1024px maximum, or the narrower composition measure documented by its pattern. The H1 and supporting paragraph follow the universal fixed **24px** rhythm from `typography.md`; the paragraph then keeps 24px to the CTA row. Never stack both margin and container gap to double either interval.
- **One element owns the vertical padding — never two nested.** When a band, card, or CTA sits inside a section, **only one of them adds vertical padding**. A section and an inner band must not both pad top/bottom, or the block bloats and reads off-center. Decide which container owns the vertical rhythm and zero the padding on the other.
- **Newsletter / signup bands get a dedicated layout — not the button-actions slot.** A CTA that holds an **email field + submit button** is a signup row, not a button group: never drop it into a `cta-card__actions` (or any container built for side-by-side buttons). Build a dedicated band — a **two-column grid on desktop** (copy left, form right) with a **hero-style signup row**: a **full-width field shell + button, inline from ~640px up and stacked below that**. Give it a responsive title, a `font-size-lg` description, and a small helper line (e.g. "No spam. Unsubscribe anytime.") under the form. **Never a fixed narrow field width** (e.g. 18rem) beside a large button — the field flexes to fill the row.
- **Reset native element margins inside cards.** Elements the browser margins by default — `<blockquote>`, `<figure>`, `<p>`, `<ul>` / `<ol>` — are set to **`margin: 0`** whenever they are, or sit inside, a card. Otherwise the user-agent's default margin leaks **outside** the card border and reads as phantom padding around the box (a `<blockquote>` testimonial card is the classic trap). All spacing comes from the card's own padding. Also delete dead modifier classes that style nothing (e.g. unused `--1` / `--2` / `--3` variants).
- **Never delete a CSS rule without proving nothing uses it.** Before removing or "deduplicating" any style, **search the whole codebase for every class / selector it targets** (markup, components, templates, JS) and confirm **zero** references remain. A selector that appears only once in the stylesheet is **not** dead if any element still carries that class — deleting it drops that section to **unstyled HTML**. Deduplicate by **consolidating** repeated declarations into one rule, never by blindly deleting; when in doubt, keep it. After any CSS cleanup, **load the page and confirm every section still renders styled** — then hard-refresh (the dev server may still serve the old CSS bundle).
- **Zero a list's default left padding, not just its margin.** A `<ul>` / `<ol>` used as a layout row, nav, or menu carries the browser's default **~40px left padding** (`padding-inline-start`, reserved for bullets) — `margin: 0` and `list-style: none` do **not** remove it. Explicitly set **`padding: 0`** (or `padding-inline: 0`); if you only set `padding-block`, that left inset stays and the whole row is pushed ~40px inward, misaligning it with the logo / page container. Let the page container own horizontal alignment — the list contributes no indent of its own.
- **Sidebar links separate hover from current state.** A plain sidebar anchor stays transparent and gains only the documented underline on hover. The active / current destination may retain one persistent `hover-fill` background with `radius-md` (2px) corners so location remains visible; that fill belongs to the selected state and must not appear on inactive links merely because they are hovered. Sidebar buttons and expandable rows remain component controls and follow their own hover rules.
- **Navbar buttons use one small size and one weight; navbar links never underline.** In a navbar, **every button is the small size** — never mix small with base or large — and **all navbar buttons share the same size and the same text font-weight**, so the bar reads consistent. Plain navbar anchors stay transparent and use only a foreground-color shift on hover, with no underline in any state. Plain sidebar anchors retain the documented underline hover. Navbar and sidebar buttons never underline and keep their component-specific hover surface.
- **Dashboard brand-navbar controls use restrained state treatments.** On the blue dashboard / application top bar, neutral icon buttons rest transparent with the documented light foreground, then use `brand-medium` with white for hover, active, and open. A visible account-identity trigger made from a placeholder portrait, user name, and chevron remains transparent through hover, active, and open because the identity group already provides its affordance; keyboard focus remains visible. The primary create action rests on `brand-medium` so it stays distinct from the navbar field and deepens to `brand-strong` on hover or press. Never introduce a white or near-white hover block.
- **Application pages use one aligned two-tier shell.** The primary application navbar and the secondary view/filter toolbar are separate full-width sticky rows, stacked without overlap and aligned to the exact same centered 1280px inner container as the main content. The primary row carries identity, global search, and global actions; the secondary row carries local views and filters. Each row draws at most one bottom hairline, uses one horizontal alignment axis, and keeps every control on the mandatory Small 32px tier. The main content begins after both rows with `spacing-8` (32px) block padding and uses the documented 16px widget-grid rhythm; do not place app controls in a floating marketing-style header or give each toolbar its own unrelated width.
- **Translucent backgrounds must blur what's behind them.** Any element with a **semi-transparent / translucent fill** — a sticky or floating navbar, a frosted card, an overlay, a glass panel — **must** pair that translucency with a **backdrop blur** (`backdrop-filter: blur(...)`, plus the `-webkit-backdrop-filter` prefix for Safari). Without it, page content scrolling **underneath** shows through razor-sharp and reads as a confusing jumble. The blur turns the see-through fill into frosted glass so the element stays legible over anything; keep a tint _with alpha_ under the blur so text holds its contrast, and fall back to an opaque fill where `backdrop-filter` is unsupported. (A fully opaque background needs no blur — this applies only when the fill has alpha.)
- **Badges always use intrinsic width and tonal borders.** A badge / tag / chip / status label sizes to **its own content** with an intrinsic / `fit-content` width and an inline content-sized layout. An `auto` width alone is not sufficient because a flex column or grid may still stretch it. Disable flex growth and opt the badge out of parent-driven stretching. It never uses `width: 100%`, `min-width: 100%`, a full grid track, `flex: 1`, or any block/flex treatment that spans the row. Its exact 1px border derives from its own soft fill mixed 80% toward its matching readable foreground 20%, so the border stays in the same shade family and is only slightly darker. Alerts use the same tonal-edge formula with their own intent fill and strong accent. See `badges.md` and `alerts.md`.
- **Pricing card: 24px between the price and the CTA button.** In a pricing card, leave **24px** between the **price line** (e.g. `$249/month`) and the **CTA button** tied to it — this is the default gap unless a prompt specifies otherwise. Apply it consistently across every tier so the prices and buttons line up row-to-row.
- **Pricing tiers align by semantic rows, not arbitrary empty space.** Cards in one pricing grid stretch to equal height. Their plan headers reserve the height of the tallest title-and-description block, price lines align across the row, CTA buttons share one baseline and width treatment, and feature lists begin after the same internal divider. Use the card grid and shared internal rows to create that alignment; never insert one-off margins or oversized blank gaps into individual tiers.
- **Avatar-only triggers carry no chevron.** In a navbar / top bar, an **avatar shown on its own** (a 2px-corner photo or initials tile) is itself the trigger — do **not** put a chevron caret beside a bare avatar. A chevron is added **only when the avatar is paired with a visible label** (the person's name / role): `avatar + name → chevron` is fine, `avatar alone → no chevron`. A lone avatar plus a chevron reads as clutter; the avatar is already the affordance.
- **Joined input + button groups square the shared edges and keep input-tone seams.** When an input is **attached to buttons (or addons) on its left and/or right** — a search-with-button, a stepper, a prefix/suffix group, any segmented control where an input touches a button — the **touching edges are squared to `0` radius** so the pieces read as one seamless control. An input with a button on **both sides** has **no border radius at all**; with a button on one side it keeps the theme's radius on the free side and `0` on the joined side. Only the **outer corners of the whole group** carry the theme's normal radius. Draw exactly one 1px `#CFC3A5` input-tone separator at every shared edge; this remains true on brand heroes and navbars, where `brand-subtle` is not used for an input group's internal seams. Critically, the input's **focus border / ring must follow that squared corner too** — never let a rounded corner (or a rounded focus outline) peek out at the seam when the input is focused; the focus state matches the 0-radius joined edge exactly.
- **Card headings are 20px.** A card's heading / title — ecommerce & product cards, feature cards, pricing cards, testimonial and content cards, and cards in general — is **20px**. The **one exception is dashboard / application widgets**: a widget's heading follows the smaller, dense widget-title scale and uses `font-weight-bold` (700) so it anchors the data beneath it. Primary widget statistics use the same 700 emphasis; supporting values remain light.
- **Every non-hero page-level section heading shares one size.** All content-section headings use the same responsive **32px to 40px** size (`font-size-7xl` / 40px on wide viewports), at 400 weight and 1.2 line-height. Never create a smaller ecommerce section heading, a larger marketing section heading, or a separate documentation-section formula. Hero `h1` display type is the only page-level exception; card, modal, and dashboard-widget titles retain their component-specific scales. See `typography.md`.
- **Ecommerce navbar collapses to one row on mobile.** On narrow viewports (**< 768px**) the ecommerce header is a **single bar** — logo at the inline start, a **hamburger menu button** at the inline end. The desktop secondary content **collapses off the bar**: the search field, cart / account actions, and the whole category row are **hidden** and move into a **menu panel that opens below the bar** (search + category links + a **"View all categories"** entry). On desktop the full **two-level layout** returns — search + logo + cart / account on the top row, categories on a row beneath. Use the **same hamburger + collapsible-panel pattern as the marketing navbar** so both headers behave consistently.
- **The storefront category navigator bridges hero and content.** The featured category navigator is one flat paper card that overlaps the image hero's lower edge by `spacing-20` (80px), leaving part of the panel on the media and part on the following `#F2EAD6` section surface. It keeps the 1280px content alignment, `spacing-8` (32px) panel padding on tablet and up, 32px row gaps with 16px column gaps, and no shadow. Category cells are centered link groups with a 64px square icon tile, 16px tile-to-label gap, 18px label, and no label underline; only the icon tile receives the neutral hover fill. This overlap is the sole approved negative page-layout offset in Blueprint and must never cause page-level horizontal scrolling.
- **Ecommerce pages use ecommerce-native TypeUI sections only.** A storefront is composed from the TypeUI ecommerce catalogue: ecommerce utility/main/category navigation, searchable deal hero, featured category promotions, product-card grid or listing, commerce promotional offer, and ecommerce newsletter/sitemap/payment/legal footer. Do not fill a store page with generic marketing feature, testimonial, pricing, dashboard, or unrelated landing-page sections. Apply Blueprint tokens to the ecommerce section anatomy without changing that anatomy into another page type.
- **Modals are paper sheets.** A modal uses `neutral-primary`, a 1px `default` edge, `radius-xl`, and `elevation-none` above the scrim. Internal header and footer rules use 1px `default-subtle`. See `modal.md`.
- **Heading line-height splits at 52px.** A heading's line-height follows its **rendered font size**: only **huge headings — rendered 52px or larger** (chiefly the marketing hero `h1`) use `line-height-display` (**1**); **every heading below 52px** — section `h2` titles, band / sub-section headings, card titles, and any heading whose largest rendered size is under 52px — uses `line-height-heading` (**1.2**). Never put tight 1:1 leading on a sub-52px heading (it crowds multi-line titles); judge a responsive `clamp()` heading by its **maximum** rendered size. See `typography.md`.
- **Card treatments live in `cards.md`.** Every card-like surface on every page—marketing cards, application widgets and table shells, component specimens, ecommerce products, testimonials, event panels, illustration frames, and grouped cards—uses the exact `neutral-primary` (`#F7F1E4`) background and the same fine 1px `buffer` (`#CFC3A5`) edge. Cards use `radius-xl` and `elevation-none`; no card is borderless. Blue, coral, status, featured, and selected treatments stay inside the card as accents and never replace its background or resting edge.
- **No hover glow anywhere — cards and tables are static.** Blueprint ships **no** pointer-tracking edge-glow and **no** breathing-border hover treatment: a card's surface is identical at rest and on hover (see `cards.md`), and a **table** (data or pricing / comparison) is likewise static — its only hover feedback is the subtle neutral **row** hover tint from `tables.md`. Nothing on the page glows, lights up, or tracks the cursor.
- **20px hero and section-supporting paragraphs; 16px floor for other body text.** The primary supporting paragraph beneath every hero `h1`, page heading, or content-section heading uses `font-size-xl` (**20px**) on every viewport and page type, including marketing, storefront, application, and documentation previews. It never steps down to 18px or 16px on mobile and must explicitly outrank any general paragraph floor. Other body / paragraph / content text never renders below 16px: card body copy, list-item prose, and running text sit at `font-size-md` (16px) or larger. The only smaller exceptions are genuine micro-elements such as badges, chips, tags, table meta / captions, helper text, eyebrows, and similar tiny labels. Never shrink reading copy to make it fit; cut words instead.
- **Inline input + button pairs are width-bounded.** Wherever an input sits next to a button in one row — a newsletter signup, sign-in, search, or promo field, in **any section, on a landing page, a dashboard, or inside a card** — the **input is never wider than 400px**, and the **whole group (input + button together) is never narrower than 440px nor wider than 600px**. In practice: clamp the group to a **440–600px** band and cap the input at **≤ 400px** inside it (the button takes the remainder). This keeps the field comfortably sized and the pairing balanced — never a stretched full-width input, never a cramped one. Below the group's min width (narrow mobile), stack the button under the input rather than shrinking either past these bounds.
- **Every input keeps the universal border on focus.** Any focusable field — a text/email/password input, textarea, select, search bar, number/phone/file control, or range slider — retains its 1px `#CFC3A5` border and adds the documented brand focus outline. A **composite shell** puts that outline on the wrapper via `:focus-within`, never around the inner input alone; a **standalone input** shows it on `:focus-visible`; a **range slider** outlines its thumb. Any global focus rule must explicitly yield to this composite contract: suppress the nested input's outline and shadow with sufficient cascade priority, then draw one uninterrupted outline around the complete wrapper. Never allow both wrapper and child focus indicators to render. This is the single focus signal across every page. See `input-field.md`.
- **Every content section uses the same surface.** All content-section surface tokens resolve to `#F2EAD6`; never alternate by document order. A restrained static paper grain may appear at very low contrast without changing the perceived color.
- **The product hero and footer bookend the page.** The footer's visual panel is always a `#003488` field, including inside the approved 24px framed marketing-footer wrapper. A product-facing hero without media is also solid `#003488`; a hero with intentional full-bleed media keeps `#003488` underneath the image and uses a dark brand overlay. Both use warm-paper text and exact 1px translucent `brand-subtle` (`rgba(255, 255, 255, 0.16)`) dividers; the same quiet edge applies to every control and navbar rule drawn over the hero image. The components catalogue is documentation and instead keeps its header on the shared `#F2EAD6` section surface.
- **Display headings — no text gradients.** On marketing and landing pages, section `h2` titles render in solid `heading` ink (`#0D294E`) at 400, while the hero `h1` on the blueprint-blue band is light (`#FEF9F1`) at 900. No gradient fill, clip effect, or decorative text treatment changes this hierarchy. On app surfaces every heading is flat and solid: `h1` at 900, `h2`–`h6` at 400.
- **Hero pattern — light dots on the blue field.** The hero band carries a **full-bleed dot lattice** laid **absolutely over the whole hero region — behind the navbar, the headings, the CTAs, and the mockup** (content sits above it; the navbar goes transparent so the pattern shows through). On the `#003488` blue the dots are a soft **`rgba(255,255,255,~0.10)` white** — visible but never hard — and the layer **fades toward the band's bottom edge**. The pattern is one of the **five sanctioned dot-grid variants in `patterns.md`** — tiny filled round dots (r ≈ 1–1.5px) on a regular pitch, never lines, squares, hexagons, waves, or any stroked lattice. Never raise the dots to full-strength marks, and never use a pattern outside the hero band.
- **Mockup framing — the translucent mat.** Every product mockup, dashboard preview, or app screenshot slide is framed in **two layers**: an **outer mat** — a translucent warm field (`rgba(25, 25, 24, 0.04)` fill) with the universal **1px `#CFC3A5` border**, **2px radius**, and **8px padding** — and the **mockup surface floating inside it** with a **2px (`radius-xl`) radius** and the same **1px `#CFC3A5` hairline** — **no shadow of any kind: shadows on mockups are forbidden**. The inner surface clips its content (`overflow: hidden`) so the mockup shares the 2px corner. Never frame a mockup with a single thick border, never drop it bare on the surface, and never add a drop shadow to it.
- **Mockup spacing.** When a mockup or visual (screenshot, app preview, product shot, device frame, illustration) is stacked with text above or below it, leave **~52px** between the mockup and the adjacent content — both above and below — so the visual reads as its own block and never crams against the copy.
- **Prohibited sections are binding.** Each module closes with hard constraints — treat them as such, not as suggestions.

## Canonical vs. summary files

Some installs ship two layers:

| Layer                 | Where                                                             | Use for                                                                                      |
| --------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **Canonical modules** | This directory (`colors.md`, `buttons.md`, …)                     | Full anatomy, tokens, states, accessibility, and prohibited rules — read before implementing |
| **Summary stubs**     | Optional nested skill folder (e.g. `.agents/skills/`, `.cursor/`) | Quick orientation and links into the canonical modules                                       |

Summaries are indexes, not substitutes. If a stub and a module ever disagree — on a color, a size, a variant, anything — **the module in this directory wins.**
